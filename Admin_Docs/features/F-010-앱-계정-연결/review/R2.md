## 지적 (있을 때)
- [신규] [주의] [확실] 로그아웃이 "판" 번호를 먼저 올리고 로그인 상태(signedOut)는 보관함 읽기 · 지우기 두 번을 기다린 뒤에야 바꾼다. 그 사이(상태는 아직 signedIn)에 시작된 `authorizedRequest` · `refreshAccessToken`은 이미 올라간 새 번호를 잡으므로, 판 번호 확인이 모두 통과한다. 그래서 (가) 그 틈에 갱신이 시작되고(액세스 토큰이 30초 안에 만료되거나 401 뒤 다시 받기) 보관함 읽기가 로그아웃의 지우기보다 먼저 처리되면, 회전된 새 리프레시 토큰이 로그아웃 뒤에 보관함에 저장되고 액세스 토큰도 메모리에 남는다. 로그아웃이 서버에 폐기를 알리는 것은 옛 토큰이라 새 토큰은 서버에서도 살아 있다. 다음에 앱을 켜면 이메일 없이 "로그인됨"으로 열린다. (나) 읽기가 지우기보다 늦게 처리되면 `expireSession`이 같은 번호로 통과해 로그아웃 뒤 상태를 'expired'로 덮는다(토큰은 지워짐). 동기화 화면의 [로그아웃]은 동기화가 도는 중에도 누를 수 있어(`sync.tsx`에서 `disabled={loggingOut}`만 확인) 이 틈에 닿을 수 있다. 틈은 보관함 작업 두 번 길이(수~수십 ms)라 드물다 — `app/src/services/session.ts` `logOut()` · `refreshAccessToken()` · `authorizedRequest()` — 확인 범위: diff의 session.ts 전체를 읽고 순서를 따라감, sync.tsx의 로그아웃 버튼 조건을 grep으로 봄. 실행해서 재현하지는 않았고, 패킷의 테스트 목록에 "갱신이 로그아웃 시작 뒤 · 상태가 바뀌기 전에 시작되는" 경우는 없다 — 로그아웃 첫 줄에서 판 번호를 올리는 것과 같은 동기 구간에서 `accessToken = null`과 `useAuthStore.setState({ status: 'signedOut', ... })`까지 먼저 하고(이러면 `refreshAccessToken`의 signedIn 확인에서 막힌다), 그 뒤에 보관함 읽기 · 지우기 · 서버 폐기를 한다. 이 순서를 만드는 테스트를 하나 더한다.
- [신규] [제안] [확실] 내려받기에서 요청한 번호(`item.id`)와 응답 본문의 `id`가 같은지 보지 않고 응답의 `id`로 폰에 넣는다. 우리 서버라면 같겠지만, 다르면 엉뚱한 번호로 기록이 들어가고(덮어쓰기는 INSERT OR IGNORE로 막힘) 요청한 번호는 계속 비어 [지금 동기화]마다 다시 받는다 — `app/src/services/sync.ts` `downloadOne()`, `app/src/domain/syncMapping.ts` `fromServerRun()` — 확인 범위: diff에서 두 함수를 읽음 — `downloadOne`에서 `run.id !== id`면 모양이 틀린 기록과 같이 건너뛴다.

## 체크 항목별 근거 (항상 작성, 항목당 한 줄)
