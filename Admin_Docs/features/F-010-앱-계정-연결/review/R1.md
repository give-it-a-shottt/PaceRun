## 지적 (있을 때)
- [제안] [확실] `isObject` 타입 가드가 두 파일에 따로 있다. 하나는 배열을 객체로 보고(apiClient) 다른 하나는 배열을 뺀다(syncMapping). 이름이 같은데 동작이 달라 나중에 헷갈린다 — `app/src/services/apiClient.ts`(isObject), `app/src/domain/syncMapping.ts`(isObject) — 패킷 diff에서 두 정의를 직접 읽음 — 한 곳(예: domain의 작은 유틸)에 두고 배열 처리를 맞추거나, apiClient 쪽 이름을 용도에 맞게 바꾼다.
- [제안] [확실] 구간(run_segments) 저장 SQL이 중복이다. 기존 러닝 끝 저장(runsRepo 164~175줄 부근, `INSERT INTO run_segments`)과 새 `insertDownloadedRun`(316줄, `INSERT OR REPLACE INTO run_segments`)이 같은 칸 · 같은 반올림을 따로 쓴다. 칸이 바뀌면 두 곳을 고쳐야 한다 — `app/src/db/runsRepo.ts`(insertDownloadedRun, 기존 구간 저장부) — b8176c6 파일에서 grep과 해당 줄을 직접 읽음 — `insertPoints`처럼 `insertSegments(db, runId, segments)` 함수로 뽑아 두 곳이 같이 쓴다.
- [제안] [확실] `logOut()`(session.ts)이 동기화의 개념인 `unsendableCount`를 직접 0으로 맞추고, 로그아웃에 반응해 기억을 지우는 일은 sync.ts 맨 아래의 모듈 로드 시점 `useAuthStore.subscribe`가 맡는다. 같은 "로그아웃 때 정리"가 두 모듈에 나뉘어 있고, sync.ts를 import해야만 정리가 작동한다 — `app/src/services/session.ts`(logOut), `app/src/services/sync.ts`(파일 끝 subscribe) — 두 파일의 diff를 직접 읽음 — 정리 책임을 한 곳으로 모은다(예: sync.ts에 `resetSyncMemory()`를 내보내 logOut이 부르거나, `unsendableCount` 초기화도 subscribe 쪽으로 옮긴다). 지금은 동작에 문제 없다.
- [제안] [추정] `SERVER_LIMITS`가 "server/app/schemas/run.py와 같아야 한다"는 주석에만 의존한다. 서버 값이 바뀌면 조용히 어긋난다(Q-006 임시 처리와 관련) — `app/src/domain/syncMapping.ts`(SERVER_LIMITS) — 서버 schemas/run.py는 열지 않아 실제 일치 여부는 모름. R4가 계약을 견주는 항목이라 일치 확인은 R4에 맡김 — 값이 어긋나는지 잡으려면 서버 값을 읽는 계약 테스트나 api-list.md 표에 상한을 한 곳으로 적어 둔다.
