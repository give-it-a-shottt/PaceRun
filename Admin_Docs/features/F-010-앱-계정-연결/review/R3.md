## 지적 (있을 때)
- [주의] [확실] 내려받기 중 기록 한 건의 GET이 4xx · 5xx로 실패하면 동기화 전체가 멈춘다. 그 기록이 목록에 남아 있는 한 이후 기록은 계속 내려받지 못하고 lastSyncAt도 적히지 않는다("서버 문제"로만 표시). 올리기 쪽은 409/413/422를 건너뛰는데 내려받기 쪽에는 같은 처리가 없다. 폰 DB에 넣다 실패한 경우(insertDownloadedRun 예외)도 같은 경로로 "서버 문제"가 된다 — services/sync.ts downloadMissing · runOnce — 패킷 diff의 sync.ts 전체와 sync.test.ts의 테스트 이름 목록을 확인(내려받기 테스트 5개 중 한 건 실패 · 404 경우 없음) — 항목별 GET을 try/catch로 감싸 ApiError(404 · 409 · 422 등 거절)는 건너뛰고 계속, 연결 실패 · 만료만 위로 던진다. 건너뛴 수를 로그로 남기고 테스트 한 개를 추가한다.
- [제안] [추정] 동기화가 도는 중 로그아웃하면 로그인이 되살아나거나 상태가 어긋날 수 있다. refreshAccessToken이 await 사이에 로그아웃되면 SecureStore.setItemAsync로 새 리프레시 토큰을 다시 저장하고(다음 실행 때 signedIn), 401이면 expireSession이 status를 'expired'로 바꿔 이메일 없는 만료 화면이 된다 — services/session.ts refreshAccessToken · expireSession · logOut — 코드를 읽고 판단했지만 실제 겹침은 실행하지 않았다. 로그아웃 중 동기화를 돌려 보거나 session.test.ts에 "갱신 중 로그아웃" 경우를 넣으면 [확실]이 된다 — 갱신 끝에 status가 아직 signedIn인지 확인하고 아니면 저장하지 않는다(로그아웃 시 세대 번호를 올려 비교).
- [제안] [확실] startSession이 리프레시 토큰을 저장한 뒤 이메일 저장에서 실패하면 예외로 "로그인 실패"가 화면에 나오지만 보관함에는 리프레시 토큰이 남아 다음에 켜면 로그인된 상태가 된다 — services/session.ts startSession — 패킷 diff의 session.ts 읽음. session.test.ts의 "보관 실패면 로그인 아님"은 첫 저장 실패만 다루는 것으로 보임(테스트 본문은 열지 않음) — 이메일 저장 실패 시 리프레시 토큰도 지우거나, 이메일 저장은 실패해도 진행한다.
- [제안] [확실] 새 DB 함수 5개(listUnsyncedRunIds · countUnsyncedRuns · markRunSynced · listRunIds · insertDownloadedRun)와 화면 훅 2개에 테스트가 없다. 특히 insertDownloadedRun의 "같은 번호면 넣지 않음"과 점 · 구간 삽입 중 실패 시 롤백은 코드로만 확인했다(withWriteTransaction이 withTransactionAsync로 감싸 롤백됨을 database.ts에서 확인). 패킷에 에뮬레이터 실행 확인은 있으나 실패 · 롤백 경우는 실행하지 않았다 — db/runsRepo.ts — 패킷의 테스트 결과 · diff 확인 — 도구 부담이 크면(D-001) insertDownloadedRun만이라도 가짜 db로 changes === 0 경로를 테스트한다. 안 해도 되는 선택이다.
