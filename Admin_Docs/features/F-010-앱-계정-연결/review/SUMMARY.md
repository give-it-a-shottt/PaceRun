## 최종 판정 (AI 위임 판정 — 사용자 확인 전)
- 수용할 지적과 이유: [주의] 2개 전부와 [제안] 가운데 아래 셋을 뺀 전부.
  - 로그아웃과 겹친 갱신: 로그인 "판" 번호를 두고 로그인 · 로그아웃할 때마다 올린다. 서버에 다녀온 사이에 번호가 바뀌었으면 새 토큰을 저장하지 않고 서버에도 폐기를 알리며, 상태도 바꾸지 않는다. 테스트 2개를 붙였다(갱신이 성공으로 돌아온 경우, 거절로 돌아온 경우).
  - 내려받기 한 건의 실패: 서버가 그 기록을 주지 않거나(4xx) 모양이 틀리거나 폰에 넣다 실패하면 그 기록만 건너뛴다. 서버에 닿지 못함 · 서버 오류(5xx) · 만료는 뒤의 기록도 같을 것이라 멈춘다. 테스트 3개.
  - 끝 시각: 끝 시각을 "시작 + 경과 시간" 이상으로 맞춰 올린다(서버의 검사를 통과한다). 테스트 2개.
  - 이메일 저장 실패: 먼저 넣은 토큰을 도로 지운다. 테스트 1개.
  - 내려받은 러닝의 크기: 서버가 받는 크기(경로 20000점 · 구간 1000개 · 이름 50자)를 넘는 응답은 받지 않는다. 테스트 1개.
  - 스토어 빌드의 주소: 개발 빌드가 아니면 `https://` 주소를 줬을 때만 요청을 보낸다. 주소가 없거나 `http://`면 보내지 않고 "서버에 연결하지 못했어요"로 알린다. 테스트 2개.
  - DB 함수: 가짜 DB 테스트 7개를 붙였다(올릴 것 찾기 · 표시 · 내려받은 러닝 넣기 · 같은 번호 · 여러 문장 · 실패 때 되돌리기).
  - 구조: 모양 확인 함수를 `domain/guards.ts` 하나로, 구간 넣기를 함수 하나로 모았다. data-model.md 표에 두 줄(구간 1000개, 끝 시각)을 더하고 feature.md의 API 목록에서 `GET /me`를 뺐다.
- 거절할 지적과 이유:
  - 로그아웃 정리를 한 모듈로: `session`이 `sync`를 부르면 두 모듈이 서로를 import하게 된다. 지금처럼 `sync`가 로그인 상태가 바뀌는 것을 지켜보는 편이 한쪽 방향이다. 까닭을 코드에 적었다.
  - 내려받기 요청을 묶기 · 바뀐 것만 받기: 서버에 "여러 건을 한 번에" · "이 시각 이후"를 받는 API가 없다. 내려받기는 로그인 직후와 [지금 동기화]에서만 돌고(D-010), 1인용이라 기록이 수천 건을 넘지 않는다. 느려진 것이 재어지면 서버 API부터 더한다.
  - 화면 훅의 테스트: 화면 훅을 테스트에서 띄우는 도구가 없다(D-001).
- 다음에 고칠 것: Q-006의 답에 따라 서버 상한을 넘는 기록의 처리를 바꾼다.
