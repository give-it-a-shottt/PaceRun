## 지적 (있을 때)
- [제안] [확실] 계획 시트와 시작 전 설정 시트가 "모드 4개 카드 + 모드 바꿀 때 값 되살리기" 흐름을 각자 갖고 있다. `selectMode`(열 때 채운 값 → 마지막 설정 → 기본값)와 `radiogroup` + `MODE_ORDER.map(ModeCard)` 블록이 거의 같다 — components/plan/WorkoutSheet.tsx `OpenSheet`, components/run/RunSetupSheet.tsx `OpenSheet` — 두 파일 전체를 읽어 비교 — 값을 되살리는 순서를 한 훅(예: `useModeConfig(initial)`)이나 `ModeSelector` 부품으로 빼면 한쪽만 고쳐서 두 시트가 어긋나는 일이 없다. 지금 중복은 약 15줄이라 급하지 않다. 주석에 "시작 전 설정 시트와 같게"라고 적어 둔 것이 중복을 인정하는 표시이기도 하다.
- [제안] [확실] 기능 사이에 상수와 함수를 컴포넌트 파일에서 가져다 쓴다. (1) WorkoutSheet가 `MODE_ORDER` · `modeDescriptions`(순수 값·함수)를 RunSetupSheet.tsx에서 import — 시트 하나를 쓰려고 시작 흐름 모듈(useStartRun · permissions)까지 끌려 들어온다. (2) 템플릿 화면(app/plan/templates.tsx)이 `PLAN_SAVE_ERROR`를 WorkoutSheet.tsx에서 import — 화면이 다른 부품 파일에 기대고 있다 — 위 두 파일과 import 줄 확인 — `MODE_ORDER` · `modeDescriptions`는 domain(예: runConfig.ts나 runView.ts), `PLAN_SAVE_ERROR`는 domain/plan.ts 또는 plan 폴더의 작은 파일로 옮기면 의존이 `components/run` ↔ `components/plan` 사이에 생기지 않는다.
- [제안] [확실] 템플릿 카드의 `MODE_COLOR`가 ModeBadge.tsx의 `BADGE`와 같은 색 토큰 대응표다(주석에도 "같은 토큰"이라 적혀 있다). ModeBadge는 이미 `MODE_ICON`을 내보내 ModeCard와 나눠 쓰는 선례가 있다 — components/plan/PlanTemplateCard.tsx, components/ModeBadge.tsx — 두 파일의 표를 비교 — ModeBadge에서 색 표(`MODE_COLOR`)도 내보내 쓰면 모드 색을 바꿀 때 한 곳만 고친다. 같은 파일의 체크 동그라미 크기 상수(CHECK_SIZE · EMPTY_CHECK_SIZE · EMPTY_CHECK_BORDER)도 ModeCard.tsx와 같은 값이 복사돼 있다(값 자체는 디자인 영역이라 보지 않음, 복사된 사실만 지적).
- [제안] [확실] 템플릿 정의에 같은 값이 두 번 적혀 있다. (1) `summary` 문구("1분 달리기 + 1분 30초 걷기 × 8", "20분, 분당 170걸음", "3km, 목표 ±10초")가 같은 파일의 `INTERVAL_INTRO` · `CADENCE_PRACTICE` · `PACE_KEEP` 값을 손으로 다시 쓴 것이라 값을 고치면 문구가 틀어질 수 있다. (2) `PACE_KEEP`(390초/km · 3000m)은 domain/runConfig.ts `defaultConfigFor('pacemaker')`의 기본값과 같은 숫자다(runConfig.ts:35) — domain/plan.ts, domain/runConfig.ts — 두 파일 읽음 — summary는 `describeConfig(config)` 결과를 쓰거나 최소한 테스트에서 맞는지 확인, 숫자는 runConfig의 상수를 가져다 쓰면 한 곳이다. 값 자체는 "Q-004 임시 처리와 관련".
- [제안] [확실] 저장 실패 안내(`SaveErrorNotice` + `notice` 번호 + 3초 타이머 `NOTICE_DURATION_MS`)가 WorkoutSheet에 직접 들어 있고, 3초와 모양은 components/Toast.tsx의 `TOAST_DURATION_MS` · 토스트 모양을 복사한 것이다. 시트 위에 그려야 하는 사정(Modal 뒤에 토스트가 가려짐)은 맞다 — components/plan/WorkoutSheet.tsx, components/Toast.tsx, state/toastStore.ts — 세 파일 읽음 — 시트 위 토스트가 다른 시트에도 필요해질 때(RunSetupSheet의 `GpsNotice`가 이미 비슷한 자리) 공용 `SheetNotice` 부품과 `TOAST_DURATION_MS` 내보내기로 합치는 것을 고려. 지금은 한 곳이라 급하지 않다.
- [제안] [확실] 템플릿 화면의 타입 import 경로가 섞여 있다. 같은 파일에서 `PLAN_TEMPLATES`는 `@/domain/plan`에서, `PlanTemplate` 타입은 `@/services/planData`(domain 타입을 다시 내보낸 것)에서 가져온다. PlanDayRow · PlanTemplateCard도 타입을 services 재내보내기로 받는다. 폴더 규칙(화면 → 서비스 → domain)을 어기진 않지만 한 타입이 두 길로 오가므로 하나로 정하는 게 읽기 쉽다 — app/plan/templates.tsx, services/planData.ts 1~6행 — 해당 파일 읽음 — 타입은 한 곳(domain에서 직접 또는 services 재내보내기)으로 통일.

## 체크 항목별 근거 (항상 작성, 항목당 한 줄)
- 프론트 구조: 컴포넌트 책임이 하나인가 → app/(tabs)/plan.tsx · app/plan/templates.tsx · WorkoutSheet.tsx · usePlanView.ts(diff) → 통과. 계획 탭은 훅(읽기)·시트(저장)·부품(그리기)으로 나뉘어 있고, 템플릿 화면의 덮어쓰기 확인 흐름은 화면 안 상태 관리라 계산 로직은 아님. 위 지적 1·2만 있음
- 프론트 구조: 공용 부품에 더한 것이 그 부품의 책임에 맞는가 → TopBar.tsx(`action`, `background`), Screen.tsx(`background`), RunSetupSheet.tsx(`MODE_ORDER` · `modeDescriptions` 내보내기) 전체 열람 → TopBar · Screen은 색 이름과 아이콘 버튼을 받기만 해 책임에 맞고, 안 주면 기존 동작 그대로. RunSetupSheet의 내보내기는 지적 2
- 프론트 구조: 폴더 구조가 overview/architecture.md와 맞는가 → architecture.md 폴더·의존 방향 절, 변경 파일 import 줄 → 맞음. domain/plan.ts는 React · Expo · DB를 import하지 않고, planData(services)가 db와 domain을 잇고, 화면은 services · domain을 부름. domain 파일 안 의존도 home · runConfig · runView · week 쪽 한 방향. architecture.md가 planData를 서비스 목록에 이미 적음
- 프론트 구조: 상태를 둔 위치(로컬/전역/서버 상태) → usePlanView.ts, WorkoutSheet.tsx, templates.tsx → 적절함. 계획은 화면 로컬 훅 상태(요청 번호로 늦은 응답 무시), 시트·템플릿 화면의 busy · 선택은 로컬, 설정은 기존 settingsStore를 읽기만 함. 새 전역 상태 없음
