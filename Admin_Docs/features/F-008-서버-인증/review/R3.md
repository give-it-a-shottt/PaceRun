## 지적 (있을 때)
- [주의] [확실] 가입 경쟁 상황(사전 조회는 통과했지만 flush에서 UNIQUE 위반)을 409로 바꾸는 분기가 테스트에 없다 — server/app/services/auth_service.py signup의 `except IntegrityError`, server/tests/test_auth.py — diff 전체와 테스트 파일 전체를 읽음. 중복 가입 테스트는 사전 조회 분기(`select ... is not None`)만 탄다 — 사전 조회를 monkeypatch로 None으로 만들거나 이미 있는 이메일을 직접 INSERT한 뒤 flush 경로를 태우는 테스트를 추가해 409 EMAIL_TAKEN과 세션 상태(rollback 후 재사용 가능)를 확인한다.
- [제안] [확실] 테스트가 `get_db`를 `lambda: db`로 갈아끼워서, 실제 `get_db`의 예외 시 rollback · 마지막 close 경로와 "예외 뒤 FOR UPDATE 잠금이 풀리는지"는 어떤 테스트도 지나가지 않는다. 500 응답(`handle_unexpected`)을 확인하는 테스트도 없다 — server/tests/conftest.py client 픽스처, server/app/db.py get_db, server/app/errors.py handle_unexpected — conftest와 errors/db diff를 읽음 — 일부러 예외를 던지는 임시 라우트를 붙여 500 `INTERNAL` 본문에 스택·SQL이 없는지 확인하는 테스트 1개를 추가한다(`raise_server_exceptions=False` 필요).
- [제안] [추정] 500 응답은 CORS 미들웨어 바깥(ServerErrorMiddleware)에서 만들어져 `Access-Control-Allow-Origin`이 안 붙을 수 있다. 그러면 웹(F-011)에서 서버 오류가 "네트워크 오류"로 보인다 — server/app/errors.py handle_unexpected, server/app/main.py 미들웨어 순서 — 코드만 읽고 실행은 안 함. 확인 방법: 위 임시 라우트로 `Origin: http://localhost:5173`을 붙여 500을 내고 응답 헤더를 본다. 헤더가 없으면 F-011 전에 처리 방식을 정한다.
- [제안] [추정] 같은 리프레시 토큰으로 정상 요청 두 개가 거의 동시에 오면(웹 탭 두 개 등) 두 번째가 "이미 쓴 토큰"으로 판정돼 그 회원의 토큰이 모두 끊긴다. 보안상 의도된 동작이지만 정상 사용자도 로그아웃될 수 있다 — server/app/services/auth_service.py refresh — 코드만 읽음, 패킷에 이 경쟁 상황 테스트가 없다고 명시됨. 확인 방법: 두 스레드로 동시에 갱신해 결과를 본다. 필요하면 "방금(수 초 이내) 교체된 토큰"은 revoke_all 없이 401만 주는 유예를 두는 것을 검토한다.
- [제안] [확실] 쿠키 방식 갱신이 INVALID_REFRESH로 실패해도 쓸모없어진 `pr_refresh` 쿠키를 지우지 않는다(로그아웃만 지운다). 다음 요청에서도 같은 실패를 반복한다 — server/app/routers/auth.py refresh — 라우터 diff를 읽음 — 쿠키 방식에서 AppError가 나면 쿠키를 삭제하는 응답을 주거나, 클라이언트(F-011)가 401 INVALID_REFRESH를 받으면 로그인 화면으로 보내도록 문서에 적는다.
