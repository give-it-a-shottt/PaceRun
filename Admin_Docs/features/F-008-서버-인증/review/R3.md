## 지적 (있을 때)
- [주의] [추정] 예상 못 한 오류(500)의 응답에 CORS 헤더가 붙지 않을 수 있다. 웹(F-011)에서는 서버가 준 `INTERNAL` 코드와 문구 대신 "네트워크 오류"로만 보일 수 있다 — server/app/main.py(CORSMiddleware 등록)와 server/app/errors.py(`handle_unexpected`) — 두 파일을 커밋 9de66d9 기준으로 읽었고 실행은 안 했다. Starlette는 `Exception` 핸들러를 가장 바깥 미들웨어(ServerErrorMiddleware)에서 처리하므로 CORS 미들웨어를 거치지 않는다는 것은 내가 아는 동작이고, 이 버전에서 직접 확인하지는 않았다(패킷도 "확인하지 않음"으로 적음). [확실]이 되려면: 허용된 Origin 헤더를 붙여 500이 나는 요청을 보내 응답 헤더에 `access-control-allow-origin`이 있는지 본다. 없다면 `handle_unexpected`에서 허용 Origin이면 헤더를 직접 붙이거나, CORS를 가장 바깥에 두는 구조로 바꾼다. 테스트도 같이 추가한다.
- [주의] [추정] 트랜잭션 롤백 경로(`get_db`의 `except: rollback()`)를 검증하는 테스트가 없다. 테스트가 `get_db`를 통째로 덮어써서(conftest.py `client` 픽스처, TestErrorFormat 500 테스트) 실제 `get_db`는 한 번도 실행되지 않는다. 특히 `refresh`는 `stored.revoked_at = now` 후 `_issue_tokens`에서 실패하면 "옛 토큰만 못 쓰게 되고 새 토큰은 못 받는" 상태가 될 수 있는데, 롤백이 돼야 안전하다 — server/app/db.py(`get_db`), server/app/services/auth_service.py(`refresh`), server/tests/conftest.py — 코드는 읽어 롤백 설계가 맞다고 봤다. 다만 테스트 실행 결과로 증명된 것은 아니다. [확실]이 되려면: 진짜 `get_db`(또는 같은 구조의 세션)를 쓰는 테스트에서 `_issue_tokens`가 예외를 던지게 만들고, 요청 뒤 옛 토큰으로 다시 갱신이 되는지 확인한다. 위 테스트를 하나 추가한다.
- [신규] [제안] [확실] 가입 중 `IntegrityError`가 나면 원인과 상관없이 모두 409 `EMAIL_TAKEN`으로 답한다. 지금 `users`에서 걸릴 수 있는 제약은 이메일 UNIQUE와 `weekly_goal` CHECK(기본값이라 사실상 안 걸림)뿐이라 지금은 문제가 없다. 하지만 제약이 늘면 엉뚱한 "이미 가입된 이메일" 메시지가 나갈 수 있다 — server/app/services/auth_service.py `signup`의 `except IntegrityError` — 해당 코드를 직접 읽음 — 제약 이름(`error.orig.diag.constraint_name == "uq_users_email"`)을 확인하고, 다르면 다시 던져 500으로 보낸다.
- [신규] [제안] [확실] 일부 입력 오류 경로에 테스트가 없다. 로그인의 422(이메일 형식 오류, 73자 이상 비밀번호), 리프레시 토큰 본문이 512자를 넘는 422, 405(허용하지 않은 메서드) 응답 형식 — server/tests/test_auth.py 전체 테스트 이름과 단정(assert) 목록을 읽음 — 위 경우를 짧은 테스트로 추가한다. 이 외에 동시 갱신(FOR UPDATE 대기 경로)이 실제 두 연결로 검증되지 않았다는 점은 패킷에 이미 적힌 한계라 중복 지적하지 않는다.

## 체크 항목별 근거 (항상 작성, 항목당 한 줄)
- 프론트: 로딩·에러·빈 데이터 상태 처리 → 해당 없음 (이유: 서버만 바뀐 기능)
- 프론트: 네트워크 실패 → 해당 없음 (이유: 서버만 바뀐 기능)
- 프론트: 입력 오류 메시지 → 해당 없음 (이유: 서버만 바뀐 기능, 서버 쪽 422 형식은 아래 상황별 응답 코드에서 다룸)
- 백엔드: 상황별 응답 코드 → errors.py, auth_service.py, deps.py, schemas/auth.py → 401(토큰 없음·만료·잘못된 로그인·갱신 실패, WWW-Authenticate 포함)·404·405·409(EMAIL_TAKEN)·422(VALIDATION, 입력값은 응답에 넣지 않음)·500(INTERNAL, 내부 정보 없음)을 한 가지 형식으로 처리. 400·403은 이 기능에 해당 상황이 없어 쓰지 않음. 500의 CORS 헤더는 위 지적 1
- 백엔드: 트랜잭션 롤백 → db.py `get_db`, auth_service.py(signup의 `db.rollback()`, refresh의 커밋 위치) → 설계는 맞음(예외 시 롤백, 재사용 감지는 커밋 후 401). 테스트가 `get_db`를 덮어써 롤백 경로를 검증하지 못함은 위 지적 2
- 백엔드: DB 제약 위반을 사용자 메시지로 바꾸는가 → auth_service.py `signup`, models/user.py → 이메일 UNIQUE 위반(동시 가입 경쟁 포함)을 409 EMAIL_TAKEN으로 변환하고 테스트됨. 원인 구분 없음은 위 지적 3. 주 목표 CHECK는 pydantic 422가 먼저 막음
- 백엔드: 외부 API 실패 대응 → 해당 없음 (이유: 외부 API 호출 없음. DB 연결 실패는 500 INTERNAL로 처리되고 테스트됨)
- 테스트: 이 기능의 테스트가 있는가 → tests/test_auth.py, tests/conftest.py → 있음(33개, 별도 `_test` DB와 Alembic 마이그레이션 사용)
- 테스트: 정상·예외 경우를 둘 다 다루는가 → test_auth.py 테스트 이름·단정 목록 → 정상과 주요 예외(중복 가입, 경쟁, 틀린 로그인, 만료·재사용·유예 시간 내 재요청, 쿠키 실패 시 삭제, 500 형식, CORS)를 다룸. 빠진 입력 오류 경로는 위 지적 4
- 테스트: 통과하는가 → 패킷의 테스트 결과(pytest 33개 통과, ruff 통과, alembic check 차이 없음) → 통과 (직접 다시 실행하지 않음)
