## 지적 (있을 때)
- [제안] [확실] 로그인의 이중 방어가 읽기 어렵다. `verify_password`가 `verify(...) and password_hash is not None`으로 "해시가 없으면 False"를 보장하는데, `login`도 `or user is None`을 또 확인한다. 둘 중 하나가 빠져도 동작해서 어느 쪽이 책임인지 흐려진다 — server/app/security.py `verify_password`, server/app/services/auth_service.py `login` — b5837b7의 두 파일 전체를 읽음 — `login`에서 `user is None`일 때 먼저 더미 검증을 돌린 뒤 실패를 던지는 식으로 한 곳(예: `if user is None: verify_password(password, None); raise ...`)에 모으거나, 두 줄 모두 남기려면 "왜 두 번인지" 주석을 단다.
- [제안] [확실] 401을 만드는 방식이 두 갈래이고 helper 일부는 쓰이지 않는다. `errors.unauthorized(message, code)`의 `code` 인자는 호출처(deps.py 3곳)가 한 번도 바꾸지 않는다. 반면 서비스는 같은 401을 `AppError(status.HTTP_401_UNAUTHORIZED, ...)`로 직접 만든다(`_invalid_refresh`, 로그인 실패). 또 `AppError` 주석은 "HTTP를 몰라도 되게 코드만 갖는다"인데 실제로는 `status_code`를 갖고, 서비스는 `fastapi.status`를 import한다(architecture.md "서비스는 FastAPI의 Request · Response를 모른다"에서 말한 Request·Response는 아니고 숫자 상수라 규칙 위반은 아님) — server/app/errors.py, server/app/deps.py, server/app/services/auth_service.py — 세 파일 전체를 읽고 `unauthorized(` 호출처를 git grep으로 확인 — `code` 인자를 지우거나 서비스도 같은 helper를 쓰게 맞추고, `AppError` 주석을 "HTTP 상태 코드와 에러 코드를 갖는다"로 사실에 맞게 고친다. 서비스가 fastapi를 import하지 않게 하려면 `http.HTTPStatus`를 쓴다.
- [제안] [확실] `auth_service.refresh`가 `(User, TokenPair)`를 돌려주지만 호출하는 라우터는 `_, tokens = ...`로 user를 버린다. 쓰이지 않는 반환값이다 — server/app/services/auth_service.py `refresh`, server/app/routers/auth.py `refresh` — 두 함수를 읽음 — 반환을 `TokenPair`만으로 줄인다(나중에 F-010/F-011이 user를 필요로 하면 그때 늘린다).
- [제안] [확실] 매직 넘버. 쿠키 수명 `refresh_token_days * 24 * 60 * 60`이 라우터에 인라인으로 있고, 액세스 토큰은 `access_token_minutes * 60`을 security.py에서 계산한다. 같은 "일/분 → 초" 변환이 두 곳에 흩어져 있다. 비밀번호 상한 72는 주석이 "서버를 느리게 만드는 요청 방지"라고 이유를 설명하지만, 72라는 값은 bcrypt 한계로 오해받기 쉽다 — server/app/routers/auth.py `_deliver`, server/app/security.py `create_access_token`, server/app/schemas/auth.py — 세 파일을 읽음 — 쿠키 수명 계산을 `Settings`의 프로퍼티(예: `refresh_token_seconds`)로 옮기고, 72에는 "api-list.md와 같은 값, 근거는 상한일 뿐"이라는 한 줄을 보탠다.
- [제안] [확실] data-model.md의 refresh_tokens 행에 실제 모델·마이그레이션에 있는 `user_id` 인덱스(ix_refresh_tokens_user_id)가 적혀 있지 않다(runs 행에는 인덱스를 적었다). users의 CHECK 제약 이름도 문서에는 값 범위만 있다. 코드와 마이그레이션은 서로 일치(alembic check 통과, 패킷)하므로 문서 쪽 누락이다 — Admin_Docs/overview/data-model.md "서버" 표 vs server/app/models/refresh_token.py, alembic/versions/0001 — 세 파일을 읽고 대조 — 표의 refresh_tokens 제약 칸에 "user_id 인덱스"를 한 마디 보탠다.
- [제안] [추정] 쓴 리프레시 토큰(revoked)과 만료된 토큰 행을 지우는 곳이 diff에 없어 `refresh_tokens`가 계속 쌓인다. 갱신할 때마다 행이 1개씩 늘어난다. 지금 규모에서는 문제가 아니다 — server/app/services/auth_service.py — diff 전체에서 삭제 쿼리가 없는 것만 확인했고 다른 폴더(스크립트·작업)는 열지 않음 — 확인하려면 server/ 안에 정리 작업이 따로 있는지 찾는다. 없으면 feature.md나 troubleshooting에 "정리는 아직 없음"을 한 줄 적거나, 갱신 시 이 회원의 만료 행을 함께 지운다.

## 체크 항목별 근거 (항상 작성, 항목당 한 줄)
- 프론트 구조: 컴포넌트 책임이 하나인가 → 해당 없음 (이유: 이번 기능은 서버만 바뀜)
- 프론트 구조: 폴더 구조가 overview/architecture.md와 맞는가 → 해당 없음 (이유: 서버만 바뀜)
- 프론트 구조: 상태를 둔 위치(로컬/전역/서버 상태)가 적절한가 → 해당 없음 (이유: 서버만 바뀜)
- 백엔드 구조: 레이어(라우터 → 서비스 → DB) 분리 → server/app/routers/*, services/auth_service.py, models/* → 분리 맞음. 위 `AppError`/`fastapi.status` 지적(제안)만 있음
- 백엔드 구조: 의존 방향이 한쪽으로 흐르는가 → routers/auth.py·me.py, deps.py, services/auth_service.py, security.py의 import → 라우터 → 서비스 → 모델/security, security는 DB·HTTP를 모름. 거꾸로 import 없음
- 백엔드 구조: 비즈니스 로직이 라우터에 섞이지 않았나 → routers/auth.py `_deliver`·`refresh`·`logout` → 라우터는 쿠키·응답 모양과 "쿠키냐 본문이냐" 선택만 함. 토큰 검증·폐기는 서비스에 있음. 지적 없음
- 데이터: data-model.md와 실제 모델·마이그레이션 일치 → 문서 "서버" 표 vs models/user.py, refresh_token.py, 0001 마이그레이션 → 칸·UNIQUE·CHECK·FK CASCADE 일치. 인덱스 문서 누락만 지적(제안)
- 데이터: 관계·제약(외래키, NOT NULL, UNIQUE)이 맞는가 → 모델과 0001 마이그레이션 대조 → NOT NULL·UNIQUE(email, token_hash)·FK ON DELETE CASCADE·revoked_at만 nullable로 의도와 일치. 지적 없음
- 데이터: 마이그레이션이 기존 데이터를 깨지 않는가 → 0001 → 첫 마이그레이션이라 기존 데이터 없음. downgrade가 생성의 역순으로 정리됨. 지적 없음
- 가독성: 이름이 역할을 설명하는가 → 전체 app/ 파일 → 이름 명확(`_issue_tokens`, `_revoke_all`, `CurrentUser`, `DbSession`). 지적 없음
- 가독성: 함수·컴포넌트 길이가 과하지 않은가 → auth_service.py `refresh`(약 30줄, 분기마다 주석) → 과하지 않음. 지적 없음
