## 한눈에 보기

무엇을: 폰이 올린 러닝을 서버에 저장하고, 목록 · 상세 · 통계로 돌려주는 API. 같은 러닝을 여러 번 올려도 한 건만 남는다. 💡 비유: 택배 송장 번호를 보내는 사람이 붙여서, 같은 상자를 두 번 접수해도 한 건으로 처리된다.
왜: 계정을 연결하면 폰의 기록이 서버에 올라가야 웹 대시보드에서 볼 수 있다.

## 설계 의도 (AI 초안 — 사용자 위임, 확인 전)
출처: pacerun-design.md 0-4(WEB_01_002 · 003), 0-5 Flow C · E · 동기화 규칙, D-007

- 이 기능이 해결하는 문제: 폰에만 있는 기록은 폰을 바꾸면 사라지고, 넓은 화면에서 월 · 년 단위로 볼 수 없다.
- 완료 기준(무엇이 되면 끝인지):
  1. 로그인한 회원이 러닝을 올린다. 번호(UUID)는 폰이 정한다. 같은 번호로 다시 올리면 덮어쓰고 한 줄만 남는다(새로 저장 201, 덮어씀 200).
  2. 다른 회원이 이미 쓰는 번호로는 올릴 수 없다(409). 원래 기록은 바뀌지 않는다.
  3. 내 러닝 목록을 최신순으로 받는다. 한 번에 최대 100개, 이어서 받을 수 있다. 목록에는 경로 · 구간이 없다.
  4. 러닝 한 건의 상세(경로 · 구간 포함)를 받는다. 없는 번호와 남의 번호는 똑같이 404다.
  5. 월(날짜별) · 년(월별) 통계를 받는다: 거리 · 횟수 · 시간 합계, 주 목표를 채운 주의 수. 하루와 한 주(월요일 0시 시작)는 사용자의 시간대로 나눈다.
  6. 주간 횟수에는 10분 이상 뛴 러닝만 센다. 인정 여부는 서버가 경과 시간으로 정한다(폰이 보낸 값을 믿지 않는다).
  7. 모든 요청은 로그인이 필요하고, 내 것만 읽고 쓸 수 있다.
  8. 틀린 값(모르는 모드, 모드와 맞지 않는 목표값, 시간대 없는 시각, 범위 밖 숫자, 너무 긴 경로)은 422로 돌려보낸다.
- 화면: 없음(서버). 앱의 올리기 · 내려받기는 F-010, 웹 화면은 F-011.
- API: `PUT /runs/{id}`, `GET /runs`, `GET /runs/{id}`, `GET /stats` (overview/api-list.md "러닝" · "통계")
- 데이터: runs 테이블(overview/data-model.md "서버")

## 결과 (AI 작성 — 구현 후)
- 바뀐 파일
  - 모델 · 마이그레이션: `server/app/models/run.py`, `server/alembic/versions/0002_runs.py`
  - 스키마(요청 · 응답 모양): `server/app/schemas/run.py`, `stats.py`
  - 서비스: `server/app/services/run_service.py`(올리기 · 목록 · 상세), `stats_service.py`(통계)
  - 라우터: `server/app/routers/runs.py`, `stats.py`, 등록은 `server/app/main.py`
  - 의존성: `tzdata`(윈도우에서 시간대 이름을 읽으려면 필요)
  - 요청 크기 상한: `server/app/middleware.py`
  - 테스트: `server/tests/test_runs.py`(44개), `test_stats.py`(21개), `test_middleware.py`(11개)
- 실제 구조
  - 올리기는 SQL 한 문장(`INSERT … ON CONFLICT (id) DO UPDATE … WHERE runs.user_id = 내 번호`)으로 한다. "있는지 확인"과 "저장" 사이에 다른 요청이 끼어들 틈이 없다. 이미 있는 줄이 남의 것이면 아무것도 바뀌지 않고 409를 준다.
  - 목록은 쪽 번호가 아니라 "이 줄 다음부터"(시작 시각 + 번호)로 넘긴다. 뒤쪽으로 갈수록 느려지지 않고, 보는 사이 새 기록이 올라와도 같은 줄이 두 번 나오지 않는다. 목록을 읽을 때는 경로 · 구간 칸을 DB에서 읽지 않는다.
  - 통계는 날짜별 합계를 SQL로 구한 뒤(범위 조건이 인덱스 `user_id, started_at`을 탄다) 빈 날 · 월별 묶음 · 주 목표 달성 주는 파이썬에서 채운다. 날짜는 `timezone(시간대, started_at)`로 사용자 시간대의 날짜를 구한다.
  - 요청 크기 상한은 두 단계다. 머리글로 먼저 거르고(조각 전송은 411, 밝힌 길이가 2MB를 넘으면 413), 머리글이 거짓이어도 실제로 받은 바이트가 2MB를 넘는 순간 413으로 끊는다.
  - 목표값(config)은 모드마다 모양이 달라, 모드에 맞는 모양으로 확인한 뒤 저장한다. 모르는 칸이 오면 422다(앱과 서버의 약속이 어긋난 것을 일찍 발견).
- 설계 의도와 다른 점
  - 처음 API 목록의 `RunIn`에는 `counted`가 있었다. 인정 여부를 폰과 서버가 따로 계산하면 어긋날 수 있어, 요청에서는 빼고 서버가 `elapsed_s ≥ 600`으로 정한다(응답에는 있다).
  - 목표값 칸 이름은 폰에서는 camelCase(`runSec`), API에서는 snake_case(`run_sec`)다. 폰이 올릴 때 바꾼다(F-010).
  - 한 번에 받는 크기를 정했다: 경과 시간 24시간, 거리 300km, 경로 20000점, 구간 1000개, 요청 본문 2MB까지.
  - 경과 시간이 `끝 시각 − 시작 시각`보다 길면 받지 않는다(짧게 뛰고 경과 시간만 크게 보내 10분 인정을 받는 것을 막는다).
  - 통계는 2000~2100년 날짜만 볼 수 있다(그 밖은 날짜 계산이 넘쳐 오류가 난다).
  - 주 목표 달성 주 수는 지금의 주 목표로 지난 주까지 다시 센다 → Q-005.
  - 폰의 기록이 서버 상한을 넘는 드문 경우의 처리(경로 솎기 등)는 앱이 올릴 때 맞춘다 → Q-006, data-model.md 대응표 아래 표.
