## 지적 (있을 때)
- [신규] [주의] [추정] plan_label에 NUL 문자(\u0000)가 들어 있으면 422가 아니라 500이 날 수 있다 — server/app/schemas/run.py RunIn.plan_label(길이 상한만 있음), server/app/services/run_service.py upsert_run — 2054a11의 schema · service · test_runs.py를 읽었다. NUL을 막는 검사도 테스트도 없다. psycopg가 NUL 든 문자열을 거절하는 것은 실행해 보지 않았다. 확인 방법: plan_label="a\u0000b"로 PUT을 한 번 보내 상태 코드를 본다. 500이면 [확실]이다. 고치는 방법: plan_label에 NUL 금지 검사(field_validator)를 넣어 422로 돌려주고 잘못된 값 테스트 목록에 추가한다.
- [신규] [제안] [확실] upsert_run이 IntegrityError를 모두 "회원이 지워짐 = 401"로 바꾼다 — server/app/services/run_service.py upsert_run의 except IntegrityError — 코드를 직접 읽었다. 지금은 check 제약(ck_runs_*)이 pydantic 검사와 같아 문제가 드러나지 않는다. 나중에 제약이 늘거나 검사가 어긋나면 서버 쪽 문제가 "로그인 풀림"으로 보여 원인 찾기가 어려워진다. 고치는 방법: error.orig의 sqlstate가 23503(외래키 위반)일 때만 401로 바꾸고, 그 밖에는 그대로 다시 던져 500으로 로그에 남긴다.
- [신규] [제안] [확실] 조각 전송(chunked, Content-Length 없음)에 411을 주는 경로의 테스트가 없다 — server/app/middleware.py BodySizeLimitMiddleware, server/tests/test_runs.py(크기 상한 테스트 4개에 411 없음) — 미들웨어 코드와 테스트 함수 목록을 읽었다. 패킷도 같은 사실을 밝혔다. 고치는 방법: 미들웨어에 직접 ASGI 요청(transfer-encoding: chunked, content-length 없음)을 넣어 411과 code LENGTH_REQUIRED를 확인하는 테스트 1개를 추가한다.
- [신규] [제안] [추정] 500 경로(저장 직후 다시 읽었는데 없는 경우 INTERNAL)와 DB 쓰기 중 예상 못 한 오류가 났을 때 롤백 · 500 응답 형식을 확인하는 러닝 쪽 테스트가 없다 — server/app/services/run_service.py upsert_run 끝부분, test_runs.py 함수 목록 — 테스트 이름만 확인했다(본문 전부는 읽지 않았다). 고치는 방법: db.execute를 실패하게 만드는(monkeypatch) 테스트로 500 INTERNAL 형식과 이후 요청이 정상인지 확인한다. 정상 흐름에서는 일어나지 않는 분기라 우선순위는 낮다.
