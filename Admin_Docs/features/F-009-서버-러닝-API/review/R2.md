## 지적 (있을 때)
- [주의] [추정] 요청 본문 크기 상한이 앱 어디에도 없다. route 20000점 · segments 1000개 상한(`max_length`)은 본문 전체를 메모리에 읽고 JSON으로 푼 뒤에야 검사된다. 그래서 수십~수백 MB짜리 PUT 하나로 메모리와 CPU를 오래 붙잡을 수 있다. 게다가 FastAPI는 본문 파싱을 의존성(로그인 확인 `CurrentUser`)보다 먼저 하므로, 토큰 없는 요청도 401을 받기 전에 본문이 끝까지 읽힌다. — server/app/main.py(크기 제한 미들웨어 없음), server/app/schemas/run.py `RunIn` · `MAX_ROUTE_POINTS` — 확인한 범위: diff 전체와 c0895fd의 main.py · errors.py · deps.py를 읽었다. "파싱이 인증보다 먼저"는 FastAPI 동작 지식에 기댄 것이고 실행해 보지 않았다. 배포 프록시의 제한은 범위 밖이라 보지 않았다. — [확실]이 되려면: 토큰 없이 수십 MB 본문으로 `PUT /api/v1/runs/{uuid}`를 보내 401이 오기 전에 메모리가 오르는지 본다. 고치는 방법: 앱에 Content-Length 상한 미들웨어를 둔다. 최대 정상 요청(20000점이면 약 1MB)보다 넉넉히 2~3MB로 잡고, Content-Length 없는 chunked 본문은 읽은 바이트를 세어 끊는다. 아니면 배포 프록시 상한을 정해 architecture.md에 적는다.
- [주의] [확실] `anchor`가 9999년이면 500이 난다. period=year, anchor=9999-xx-xx면 `date(10000, 1, 1)`이 ValueError를 낸다. period=month, anchor=9999-12-xx면 `start.replace(day=28) + timedelta(days=4)`가 OverflowError를 낸다. 어느 쪽도 처리하지 않아 catch_unexpected가 500으로 돌려준다(응답에 내부 정보는 없다). — server/app/services/stats_service.py `_period_range`, server/app/routers/stats.py `anchor: date | None` — 확인한 범위: diff의 두 함수와 errors.py의 500 처리를 읽었다. 파이썬 date 상한(MAXYEAR=9999)으로 결과가 정해진다. — 고치는 방법: 라우터에서 anchor 범위를 막는다(예: 1970-01-01 ~ 9998-12-31, 벗어나면 422). 아니면 `_period_range`에서 ValueError · OverflowError를 잡아 `AppError(422, "VALIDATION")`로 바꾼다.
- [제안] [추정] `tz`는 파이썬 시간대 DB(`zoneinfo` + tzdata)로 검사한 뒤 Postgres의 `timezone()`에 넘긴다. 두 DB의 이름 목록은 같다는 보장이 없어서, 파이썬이 받는 이름을 Postgres가 모르면 DB 오류로 500이 난다. 또 윈도우에서는 `tz=Asia`처럼 폴더 이름을 넣으면 `ZoneInfo`가 PermissionError를 낼 수 있는데, 이것도 잡히지 않아 500이 된다. 인젝션은 아니다. `tz.key`는 바인드 파라미터로 들어간다. — server/app/services/stats_service.py `_zone` · `_daily_totals` · `_goal_weeks` — 확인한 범위: diff를 읽었다. 실제 이름 차이와 윈도우 예외는 돌려 보지 않았다. — [확실]이 되려면: `tz=Asia`, `tz=posixrules` 등으로 /stats를 불러 422가 아닌 500이 오는지 본다. 고치는 방법: `tz_name in zoneinfo.available_timezones()`(한 번 만들어 둔 집합)일 때만 받고, 나머지는 422로 돌려준다.
- [제안] [추정] 파이썬 `json.loads`(Starlette `request.json()`)는 `NaN` · `Infinity`를 받아들인다. pydantic float는 기본이 `allow_inf_nan=True`이고, ge/le 제약이 NaN을 막는지는 확인하지 못했다. 막지 않으면 NaN이 distance_m · route로 JSONB/float 칸에 들어간다. Postgres에서는 NaN이 모든 수보다 커서 `distance_m >= 0` CHECK도 통과한다. 그러면 그 회원의 통계 합계가 NaN이 되고, 응답 직렬화가 실패(500)할 수 있다. 영향은 본인 데이터에 한정된다. — server/app/schemas/run.py `_Strict` · `RoutePoint` · `RunIn` — 확인한 범위: diff를 읽었다. NaN 요청은 돌려 보지 않았다. — [확실]이 되려면: `distance_m: NaN`을 담은 본문을 보내 422가 오는지 확인한다. 고치는 방법: `_Strict`의 model_config에 `allow_inf_nan=False`를 넣는다(RoutePoint의 float에도 같은 제약). NaN 요청이 422인지 보는 테스트를 하나 둔다.
- [제안] [추정] 목록은 `ORDER BY started_at DESC, id DESC`와 `(started_at, id) < (…)` 커서로 읽는데, 인덱스는 `(user_id, started_at)`뿐이라 id가 없다. 이 상태면 Postgres는 커서 조건을 `started_at <=`로 느슨하게 줄여 인덱스로 찾고, 같은 시각 안의 id 정렬은 따로 한다. 지금 데이터 규모에서는 문제가 아니다. — server/alembic/versions/0002_runs.py · server/app/models/run.py `ix_runs_user_started`, server/app/services/run_service.py `list_runs` — 확인한 범위: diff를 읽었다. EXPLAIN은 돌리지 않았다(패킷에도 수천 건 측정 없음). — [확실]이 되려면: 수천 건을 넣고 커서 요청의 EXPLAIN에서 Incremental Sort나 Filter가 붙는지 본다. 고치는 방법: 인덱스를 `(user_id, started_at, id)`로 넓힌다. 그러면 정렬과 커서 조건 모두 인덱스 순서만으로 끝난다. 통계의 범위 조건도 그대로 이 인덱스를 탄다.
- [제안] [확실] 올리기 응답은 `RunSummary`(경로 · 구간 없음)인데, 저장 뒤 `db.get(Run, run_id, populate_existing=True)`로 route(최대 20000점) · segments까지 든 줄 전체를 다시 읽는다. 그래서 올릴 때마다 큰 JSONB를 한 번 더 왕복한다. — server/app/services/run_service.py `upsert_run` — 확인한 범위: diff에서 upsert_run과 RunSummary 필드를 읽었다. — 고치는 방법: RETURNING에 RunSummary 칸들을 함께 받아 응답을 만든다. 아니면 다시 읽을 때 `select(Run).options(defer(Run.route), defer(Run.segments))`를 쓴다.
