## 지적 (있을 때)
- [신규] [주의] [추정] 본문 크기 상한이 Content-Length 머리글만 믿는다. Content-Length가 있으면 Transfer-Encoding을 아예 보지 않고, 실제로 받은 바이트 수도 세지 않는다. 그래서 `Content-Length: 10`과 `Transfer-Encoding: chunked`를 함께 보내면 상한 검사를 지나간다. HTTP 파서가 두 머리글을 함께 받아 주고 RFC대로 chunked를 따르면(h11이 이렇게 동작할 수 있다) 끝없이 큰 본문이 로그인 확인 전에 메모리로 읽힌다. Content-Length 없이 본문을 보내는 프로토콜(HTTP/2 서버)에서도 통과한다. 지금 잠금 파일에 httptools가 있어 uvicorn이 기본으로 llhttp를 쓰고, llhttp는 기본 설정에서 CL+TE 요청을 400으로 거절하므로 지금 배포에서는 막힐 가능성이 크다. 다만 미들웨어 자체는 막지 못한다 — `server/app/middleware.py` `BodySizeLimitMiddleware.__call__` — 확인한 범위: 미들웨어 코드(diff)와 uv.lock의 httptools 0.9.0 · h11 0.16.0 항목. 서버를 띄워 보내 보지는 않았다. — [확실]로 바꾸려면 `uvicorn --http h11`과 기본 설정 각각에 CL+TE를 함께 넣은 3MB 요청을 원시 소켓으로 보내 413 · 400이 나오는지 본다. 고치는 방법: (1) Content-Length를 보기 전에 Transfer-Encoding부터 확인해, 있으면 무조건 411로 돌려보낸다. (2) `receive`를 감싸 받은 바이트를 더해 가다가 상한을 넘으면 413으로 끊는다. 머리글이 거짓이어도 막힌다.
- [신규] [제안] [확실] `Segment.idx`에 상한이 없다(`Field(ge=0)`만 있음). 아주 큰 정수도 받아서 JSONB에 그대로 저장한다. 본문 2MB 상한 안이라 서버가 무거워지지는 않지만, 다른 칸은 모두 상한이 있는데 이 칸만 빠져 있고, 나중에 앱 · 웹(JS number)에서 읽으면 값이 정확하지 않게 된다 — `server/app/schemas/run.py` `Segment` — 확인한 범위: 스키마 diff — 고치는 방법: `idx: int = Field(ge=0, lt=MAX_SEGMENTS)`.
