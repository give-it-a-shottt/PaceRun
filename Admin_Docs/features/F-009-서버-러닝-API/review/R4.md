## 지적 (있을 때)
- [주의] [확실] 10분 인정이 폰과 서버에서 어긋난다. 폰은 `elapsed_ms ≥ 600000`(밀리초)으로 정하는데, 서버는 폰이 "정수로 반올림"해 올린 `elapsed_s ≥ 600`으로 정한다. 599.5~599.999초를 뛴 러닝은 폰에서 counted=false, 서버에서 true가 된다. 앱과 웹의 주간 횟수가 달라질 수 있다 — data-model.md "폰 ↔ 서버 이름 대응"(elapsed_ms → 반올림), schemas/run.py `COUNTED_MIN_ELAPSED_S` 주석("앱과 같은 규칙"), app/src/domain/types.ts `COUNTED_MIN_ELAPSED_MS` — 세 곳을 직접 읽음. 앱 변환 코드는 아직 없음 — 고치는 방법: 대응표를 "내림(floor)"으로 바꾸면 두 규칙이 일치한다(floor(ms/1000) ≥ 600 ⇔ ms ≥ 600000). 반올림을 유지하려면 그 차이를 문서에 적는다.
- [주의] [확실] 폰 ↔ 서버 이름 대응표가 불완전하다. F-010에서 앱이 이 표만 보고 변환 코드를 짜면 빠진다. 표에는 elapsed_ms, run_points, run_segments, started_at만 있다. 빠진 것: ① segments의 `started_elapsed_ms → started_elapsed_s`, `duration_ms → duration_s`(서버는 둘 다 정수 초, 반올림 규칙 없음) ② route 점의 `elapsed_ms → 세 번째 값(초, 실수 허용)`, `t` · `accuracy`는 올리지 않음 ③ ended_at(폰은 null 가능, 서버는 필수 — finished만 올림) ④ ended_at도 밀리초 → ISO ⑤ config camelCase → snake_case 칸별 대응(`targetDurationSec → target_duration_sec`, `runSec → run_sec`, `walkSec → walk_sec`, `repeats`, `spm`, `durationSec → duration_sec`, `targetPaceSecPerKm → target_pace_s_per_km`, `distanceM → distance_m`)은 "예: runSec ↔ run_sec" 한 줄뿐 ⑥ 올리지 않는 폰 칸(status, sync_state, updated_at, counted) — data-model.md 대응표 · api-list.md "러닝" · app/src/domain/types.ts · app/src/db/schema.ts를 직접 비교 — 고치는 방법: 대응표에 위 항목을 칸 단위로 추가한다.
- [주의] [확실] 서버의 숫자 상한이 api-list.md에 일부만 적혀 있고, 폰 쪽은 "양수"뿐이라 정상 러닝이 영구히 422로 거절될 수 있다. 문서에 없는 상한: `avg_pace_s_per_km` > 0 · ≤ 3600, interval `run_sec` · `walk_sec` ≤ 3600, pacemaker `target_pace_s_per_km` ≤ 3600 · `distance_m` ≤ 300000 · 정수만(5000.5는 422), cadence `duration_sec` ≤ 86400, free `target_duration_sec` ≤ 86400, route 위도 ±90 · 경도 ±180, segments `idx` ≥ 0 · `kind` ∈ run/walk/km(api-list에는 없고 data-model 폰 표에만 있음). 걷듯 느린 러닝의 평균 페이스가 3600초/km를 넘으면 폰은 정상 기록인데 서버가 계속 422를 낸다(앱이 재시도해도 같음) — schemas/run.py 전체, api-list.md "러닝", data-model.md config 표를 직접 비교 — 고치는 방법: 상한을 api-list.md config 표와 필드 설명에 모두 적고, 앱이 올리기 전에 같은 범위로 막거나 고칠지(예: 페이스는 상한 없이 null 허용) 정한다. 이 상한은 feature.md "설계 의도와 다른 점"에 크기 상한 일부만 적혀 있어 의도에 없던 추가이기도 하다.
- [제안] [확실] api-list.md "러닝" 요청 설명이 선택 칸을 구분하지 않는다. 서버는 `plan_label`(null 가능, 생략 가능), `avg_pace_s_per_km`(null 가능, 생략 가능), `segments` · `route`(생략하면 빈 배열)가 선택인데, 문서의 `RunIn` 나열은 모두 필수처럼 보인다. 응답 `RunSummary`도 plan_label · avg_pace_s_per_km가 null일 수 있다고 적지 않았다 — schemas/run.py `RunIn` · `RunSummary` vs api-list.md — 고치는 방법: 필수 / 선택(null 허용)을 칸별로 적는다.
- [제안] [확실] 목록 정렬 설명이 틀리게 읽힌다. 문서는 "같으면 id 순", 서버는 `started_at desc, id desc`(id 큰 순)이고 커서도 그 기준이다 — run_service.list_runs — 고치는 방법: "같으면 id 큰 순"으로 고친다.
- [제안] [확실] 문서에 없는 입력 오류 경로가 있다. `GET /runs/{id}`의 id가 UUID가 아니면 422(문서는 PUT만 적음), `GET /stats`의 period · anchor가 틀리면 422(문서는 tz만 적음) — routers/runs.py `get_run`, routers/stats.py — 고치는 방법: 공통 422 설명에 "경로 · 쿼리 값이 틀려도 422"를 한 줄 추가한다.
- [제안] [확실] 아주 먼 anchor(9999년)를 주면 422가 아니라 500 INTERNAL이 된다. `_period_range`에서 month는 `OverflowError`, year는 `ValueError`가 난다(파이썬으로 확인) — stats_service._period_range — 고치는 방법: anchor 범위(예: 2000~2100년)를 422로 막는다. 로그인한 본인에게만 영향이라 낮은 우선순위다.
- [제안] [추정] config 검사 오류의 `fields` 형식. `RunIn._check` 안에서 모드별 config 모델의 `ValidationError`를 다시 던지므로 422 본문의 `fields[].field`가 `config.run_sec`처럼 칸 단위가 아니라 비거나 하나의 긴 message로 나올 수 있다(api-list.md는 `fields: [{field, message}]`를 약속). 테스트는 상태 코드 422만 확인한다고 패킷에 적혀 있음 — 확인: 잘못된 config로 PUT을 보내 응답 본문의 `fields`를 본다 — 고치는 방법: config를 모드별 Union(`Discriminator`)으로 받거나 칸 경로를 붙여 다시 던진다.
- [제안] [확실] 사용자가 정해야 할 제품 선택이 질문 없이 들어갔다. goal_weeks는 "지금의 `weekly_goal`"로 과거 주까지 다시 계산하므로, 주 목표를 바꾸면 과거 달성 주 수가 바뀐다. 기간 밖으로 걸친 주는 그 주 전체를 센다. api-list.md에는 적혀 있지만 feature.md "열린 질문"은 "없음"이다 — stats_service._goal_weeks, feature.md — 고치는 방법: OPEN_QUESTIONS에 "주 목표를 바꾸면 과거 달성 여부도 바뀌어도 되는가(기록 시점의 목표를 남길 것인가)"를 추가하고 답이 나올 때까지 현재 동작을 임시 처리로 표시한다.
