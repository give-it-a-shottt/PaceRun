## 지적 (있을 때)
- [신규] [주의] [확실] 폰→서버 변환 표에 config의 `mode` 칸을 빼라는 말이 없다. 폰의 `RunConfig`는 `mode`를 객체 안에 포함하고 `runs.config_json`에 `JSON.stringify(state.config)`로 그대로 저장한다. 서버 config 모델은 모두 `extra="forbid"`라서, 표대로 칸 이름만 snake_case로 바꿔 올리면 `config.mode` 때문에 모든 올리기가 422가 된다 — data-model.md "폰 ↔ 서버 이름 대응"의 config_json 줄과 "config 칸 이름" 표(mode 줄 없음) / app/src/domain/types.ts(RunConfig), app/src/db/runsRepo.ts(insertRun), server/app/schemas/run.py(_Strict, 4개 Config) — 위 4개 파일을 직접 읽고 대조했다. F-010 코드는 아직 없어 실제 호출은 못 봤다 — "config_json의 `mode`는 올리지 않는다(서버는 최상위 `mode`로 모양을 정한다)"를 표에 한 줄 추가. 서버 쪽에서 `mode` 키를 받아 주는 방법도 있으나 문서가 이미 "모르는 칸은 422"라 문서 쪽 수정이 맞다.
- [신규] [주의] [추정] 요청 크기 상한이 Content-Length와 Transfer-Encoding: chunked를 함께 보내면 우회될 수 있다. 미들웨어는 Content-Length가 있으면 그 값만 보고(작으면 통과) chunked 검사는 길이 헤더가 없을 때만 한다. 두 헤더가 같이 오면 서버(h11 계열)는 보통 chunked를 우선하므로 본문 크기는 검사되지 않는다. api-list.md는 "2MB 넘으면 로그인 여부와 관계없이 413"이라고 약속한다 — server/app/middleware.py(BodySizeLimitMiddleware.__call__) 코드만 읽었다, uvicorn이 두 헤더를 같이 받는 요청을 어떻게 처리하는지는 실행하지 않았다. 확인법: 서버를 띄워 `Content-Length: 10`과 `Transfer-Encoding: chunked`를 함께 달고 3MB를 조각으로 보내 413이 나오는지 본다. 고치는 법: Transfer-Encoding이 chunked면 Content-Length 유무와 상관없이 411, 또는 receive를 감싸 읽은 바이트를 세어 넘으면 끊는다.
- [신규] [제안] [확실] 422 응답의 `fields`가 문서 설명과 다르게 빠지거나 비는 경우가 있다. 공통 절은 "입력 오류(422)는 `fields: [{field, message}]`가 더 붙는다"고 하지만, (1) cursor 오류와 통계의 tz · anchor 범위 오류는 `AppError`로 던져 `fields`가 없고, (2) RunIn의 모델 단위 검사(config 모양 · ended_at ≥ started_at · elapsed_s 길이)는 위치가 `body` 하나라 `field`가 빈 문자열이다. config 칸 이름은 top-level `message`가 아니라 `fields[].message`에 들어간다 — server/app/services/run_service.py(_decode_cursor), stats_service.py(_validation_error), errors.py(handle_validation), schemas/run.py(RunIn._check) — 코드만 읽었고 (2)의 빈 `field`는 pydantic 동작 지식에 근거해 실행으로는 못 봤다 — api-list.md에 "cursor · tz · anchor 범위 오류는 `fields` 없음", "config · 시각 · 경과 시간 검사 오류는 `field`가 비어 있고 문구는 `fields[].message`에 있다"를 적거나, F-010 · F-011이 `fields`가 없을 수도 있다고 가정하게 한다.
- [신규] [제안] [추정] 폰이 만드는 값 중 서버 상한을 넘을 수 있는 것이 있다. 올리기가 영구히 422로 실패할 수 있어 F-010이 알아야 한다. (a) route 20000점 상한: 점은 약 1초마다 쌓이고 자유 모드는 시간 제한 없음(null)이 가능해 약 5.5시간 넘는 러닝이면 초과한다. (b) avg_pace_s_per_km ≤ 86400: 폰 `averagePaceSecPerKm`은 거리 50m 이상이면 상한 없이 계산해 아주 느리면(예: 60m를 2시간) 86400을 넘는다. (c) plan_label 50자: 폰에는 길이 제한이 없다. (d) config: 표의 "폰에서 고를 수 있는 범위는 모두 그 안"은 선택 화면 기준으로 맞지만(runConfig.ts의 CONFIG_LIMITS를 서버 상한과 대조해 확인), 저장돼 있던 값을 읽는 `isRunConfig`는 양수 · 실수도 통과시켜 서버의 정수 · 상한 검사와 어긋날 수 있다 — app/src/domain/pace.ts, settings.ts, runConfig.ts, 서버 schemas/run.py 상수 대조(앱의 올리기 코드는 없어 실제로 걸리는지는 못 봤다) — data-model.md 변환 표에 "경로가 20000점을 넘으면 줄여서 올린다 · 페이스가 86400을 넘으면 null · 라벨은 50자로 자른다 · config는 올리기 전에 정수로 맞춘다"를 적거나 Q로 올려 사용자가 정하게 한다(선택이 필요한 내용이라 임의로 정하지 않는다).
