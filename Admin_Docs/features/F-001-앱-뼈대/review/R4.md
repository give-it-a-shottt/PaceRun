## 지적 (있을 때)
- [제안] [확실] app.json에 F-001 설계 의도에 없는 네이티브 권한·플러그인이 미리 들어가 있다(ACCESS_BACKGROUND_LOCATION, FOREGROUND_SERVICE_LOCATION, POST_NOTIFICATIONS, expo-location 백그라운드, expo-notifications, expo-audio 백그라운드 재생, expo-task-manager, expo-secure-store, Pretendard 폰트). D-001이 개발 빌드 때문에 네이티브 선탑재를 정당화하고 러닝 기능(F-002~)에 필요한 것이라 어긋남은 아니지만, feature.md "설계 의도와 다른 점"에 적혀 있지 않다 — app/app.json — diff 전체와 feature.md를 대조 — "설계 의도와 다른 점"에 "뒤 기능용 권한·플러그인을 개발 빌드에 미리 포함(재빌드 최소화)"을 한 줄 추가. 권한을 줄이고 싶으면 사용자가 정할 일이다.
- [제안] [확실] settings 저장 키 이름(weeklyGoal, reminderTime, voiceEnabled, voiceIntervalKm, defaultCadenceSpm, runTheme, onboardingDone, lastRunConfig, lastSyncAt)과 값 모양(RunConfig 4종의 필드, 기본값 주 3회 · 170spm · 음성 켬 · 1km 간격)이 data-model.md에 없고 코드(domain/types.ts)에만 있다. data-model.md는 settings를 key/value(JSON) 한 줄로만 설명 — domain/types.ts, db/settingsRepo.ts — data-model.md "폰 (SQLite)" 절과 비교 — settings 값 목록과 config_json 모양을 data-model.md에 옮기거나 types.ts를 기준으로 한다는 한 줄을 적는다. 기본값(특히 음성 안내 켬, 알림 끔)은 사용자 확인이 필요한 선택이므로 feature.md 설계 의도 확인 때 같이 보이게 한다.
- [제안] [확실] mergeSettings는 JSON이 깨진 경우만 기본값으로 되돌리고, 파싱은 되지만 타입·범위가 틀린 값(예: weeklyGoal 9, runTheme "x")은 그대로 통과시킨다. 현재는 앱만 쓰므로 문제가 드러나지 않는다 — domain/settings.ts mergeSettings — 코드 직접 확인, 테스트 파일은 열지 않음 — 키별 타입·범위 검사를 추가(weeklyGoal 2~5 등, WEEKLY_GOAL_MIN/MAX 상수가 이미 있음)하고 어긋나면 기본값 사용.
- [제안] [추정] 설정 읽기가 실패하면 load()가 loaded=true와 error만 세팅하고 기본값(onboardingDone=false)으로 앱이 진행한다. error를 보여 주는 곳이 이번 범위에 없고, F-004에서 온보딩 분기를 붙이면 DB 오류 때 기존 사용자가 온보딩을 다시 보게 될 수 있다 — state/settingsStore.ts load, app/_layout.tsx — 두 파일만 확인, F-004 분기 코드는 아직 없음. 분기를 붙일 때 error 상태를 같이 보게 하면 [확실]로 판정 가능 — F-004 작업 때 error가 있으면 온보딩 분기를 하지 않거나 오류 안내를 띄우도록 처리하고, 지금은 feature.md 결과에 "읽기 실패 시 기본값으로 진행" 한 줄 기록.
