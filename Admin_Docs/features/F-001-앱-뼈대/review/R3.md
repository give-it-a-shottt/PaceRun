## 지적 (있을 때)
- [주의] [확실] 설정 읽기 실패 시 `error` 문구를 만들지만 이를 보여주는 곳이 없다. 읽기에 실패해도 `loaded: true`가 되어 앱이 기본값(`onboardingDone: false` 포함)으로 그대로 열린다 — app/src/state/settingsStore.ts `load`, app/src/app/_layout.tsx `RootLayout` — settingsStore.ts·_layout.tsx 전체와 src 아래 tsx에서 `error` 사용처 검색(사용처 없음) — 루트 레이아웃에서 `error`가 있으면 AlertDialog나 showToast로 알리고, F-004 온보딩 분기는 `loaded && !error`일 때만 `onboardingDone`을 믿도록 한다(지금 안 고치면 DB 오류 때 기존 사용자가 온보딩으로 다시 가게 될 수 있음).
- [주의] [확실] 이 기능에서 예외 처리 코드가 가장 많은 `settingsStore`(load 실패, update 실패 시 값 되돌림)와 `database.ts`(실패한 Promise 폐기 후 재시도, 마이그레이션 단계 적용)에 테스트가 없다 — app/src/state/settingsStore.ts, app/src/db/database.ts, app/src/db/settingsRepo.ts — 패킷의 테스트 목록(settings.test.ts, schema.test.ts)과 diff 확인 — `vi.mock('@/db/settingsRepo')`로 저장소 실패를 흉내 내 store 테스트를 추가하고, `getDb`의 재시도는 `expo-sqlite`를 mock해서 확인한다. 마이그레이션 단계 적용(user_version)은 node:sqlite로 "두 번 돌려도 안전, 중간 실패 시 롤백"을 확인하는 테스트를 고려.
- [주의] [확실] `mergeSettings`는 JSON이 깨진 경우만 막고, JSON은 맞지만 타입이 틀린 값(예: weeklyGoal가 `"abc"`, runTheme가 `"x"`)은 그대로 `Settings`에 넣는다. 또 `row.key in DEFAULT_SETTINGS`는 `constructor` 같은 프로토타입 키도 통과시킨다 — app/src/domain/settings.ts `mergeSettings` — settings.ts와 settings.test.ts 확인(타입 틀린 값 테스트 없음) — 키별로 값 타입을 검사해 맞지 않으면 기본값을 쓰고(`Object.hasOwn` 사용), 해당 테스트를 추가한다. 지금은 앱이 직접 쓰는 값만 들어오므로 실제 발생 가능성은 낮다.
- [제안] [확실] `update`의 실패 시 되돌림은 호출 직전 `previous` 전체로 덮어쓴다. 서로 다른 키를 연달아 바꾸다 앞 호출이 실패하면 뒤 호출의 값까지 같이 사라진다 — app/src/state/settingsStore.ts `update` — 코드 읽음 — 실패한 키 하나만 이전 값으로 되돌린다(`set((s) => ({ settings: { ...s.settings, [key]: previous[key] } }))`).
- [제안] [추정] DB 열기가 끝나지 않고 멈추면 스플래시가 계속 붙어 있고 앱이 열리지 않는다. 또 최상위 오류 경계(ErrorBoundary)가 없다 — app/src/app/_layout.tsx — 실제 멈춤은 기기에서 재현해 봐야 알 수 있음(`load`에 시간 제한을 둬 보고 확인) — `load`에 수 초 제한을 두고 넘으면 error로 처리하며, expo-router의 `ErrorBoundary` export를 루트에 둔다.
- [제안] [확실] 스키마 테스트의 "거절한다" 검사가 `toThrow()`만 써서 어떤 이유로 던져도 통과한다(예: mode 값 `'swim'` 테스트가 다른 컬럼 오류로 통과해도 모름). `run_segments.kind`, `counted`, `sync_state`의 CHECK와 `run_segments` 기본키 중복은 검사하지 않는다 — app/src/db/schema.test.ts — 파일 전체 확인 — `toThrow(/CHECK constraint failed/)`처럼 메시지를 좁히고, 빠진 제약 검사를 추가한다.
