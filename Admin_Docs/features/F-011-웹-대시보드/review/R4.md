## 지적 (있을 때)
- [제안] [확실] 기준 날짜의 아래쪽 한계를 웹이 모른다 — web/src/pages/dashboard/dashboardQuery.ts `parseDashboardQuery`(위쪽만 today로 막음), web/src/domain/dashboard.ts `shiftAnchor`, DashboardControls.tsx [이전] 버튼(막지 않음) ↔ api-list.md "통계"(anchor 2000-01-01 ~ 2100-12-31, 밖이면 422 `VALIDATION`) — 코드와 문서를 직접 읽고 비교함. 화면에서 `?anchor=1999-01-01`을 열어 보지는 않음 — 주소에 2000년 이전 날짜를 넣거나 [이전]을 2000년 아래까지 누르면(년 단위에서 2000년의 "이전 해"인 1999년, 월 단위 2000-01의 지난 기간 조회 포함) 서버가 422를 주고 화면은 "불러오지 못했어요"를 띄운다(4xx라 다시 하지 않음). 계약 위반은 아니고 모서리 동작이다. 고치는 방법: 파싱에서 2000-01-01 미만은 today처럼 기본값으로 보거나 [이전]을 막는다(막지 않고 두어도 됨).
- [제안] [추정] 리프레시 갱신이 "동시 요청"으로 401만 받는 경우(api-list.md "인증": 교체 10초 안이면 쿠키를 지우지 않고 401만 줌)에도 웹은 상태 코드 401만 보고 이 탭을 로그아웃 상태로 만든다 — web/src/api/session.ts `refreshAccessToken` · `restoreSession` — session.ts와 서버 auth.py(refresh의 RefreshRaceError 분기)를 읽고 비교함. 탭 2개를 동시에 열어 실행해 보지는 않음. [확실]이 되려면: 탭 2개를 같은 순간에 열어 둘 다 로그인 상태로 남는지 본다. 이때 쿠키는 남아 있어 새로 고침하면 다시 로그인되므로 영향은 작다. 고치는 방법: 응답의 `code`가 `INVALID_REFRESH`일 때 한 번 더 시도하거나, 지금처럼 두고 feature.md "확인하지 못한 것"에 적는다.
- [제안] [추정] `VITE_API_URL`로 다른 주소의 API를 부르게 하는 길이 열려 있다 — web/src/api/client.ts `apiBaseUrl` ↔ api-list.md(쿠키 `pr_refresh`는 SameSite=Lax, 경로 `/api/v1/auth`) · feature.md("쿠키가 실리려면 사이트와 API의 주소가 같아야 한다", 배포는 범위 밖) — 코드와 문서를 읽고 비교함. 다른 사이트(site) 주소를 실제로 써 보지는 않음. [확실]이 되려면: 다른 도메인의 API로 로그인해 refresh에 쿠키가 실리는지 본다. SameSite=Lax 쿠키는 다른 사이트로 가는 fetch에는 실리지 않으므로 그 경우 새로 고침 로그인이 안 될 가능성이 크다. 같은 사이트(서브도메인만 다름) 안에서는 동작한다. 설계 의도에 없는 설정 칸이므로 README 또는 feature.md에 "같은 사이트일 때만"이라고 한 줄 남기길 제안한다.
