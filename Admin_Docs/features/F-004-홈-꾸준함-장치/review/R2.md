## 지적 (있을 때)
- [신규] [제안] [추정] 홈이 보일 때마다 끝난 러닝 전체를 읽고, 계산이 "러닝 수 × (주 연속 주 수 + 7)"만큼 돈다. `weekProgress`는 지난주부터 거슬러 올라가며 주마다 `countedInWeek`로 러닝 전체를 `filter`(매번 새 배열)하므로 O(주 연속 × N)이다(못 채운 주에서 멈추므로 상한은 "주 연속 + 1"주). 여기에 `weekCells`가 7 × N번 `isSameDay`(호출마다 Date 2개), `todayCard`의 오늘 러닝 찾기가 N번 `isSameDay`, `nextSession`이 최대 2번 · `previousComparable`가 1번 전체를 돈다(이 셋은 O(N)이라 문제 아님). 예: 러닝 3,000건 · 주 목표 1회로 5년 이어 온 사람(주 연속 약 260)이면 주 연속 계산만 약 78만 번 비교 + 배열 260개, 칸 계산에 Date 약 4만 개가 탭 포커스 · 앱 복귀마다 JS 스레드에서 생긴다 — `domain/weekProgress.ts` `weekProgress` · `countedInWeek` · `weekCells`, `domain/home.ts` `todayCard`, `db/runsRepo.ts` `listRunDigests`, `services/homeData.ts` `loadHome` — 확인한 범위: 패킷 diff의 해당 함수 전부를 읽고 반복 횟수를 셈. 실제 걸리는 시간은 재지 않음(패킷에도 "수천 건일 때 홈이 뜨는 시간"은 미확인) — [확실]이 되려면 에뮬레이터 DB에 러닝 3,000건(주 연속이 긴 모양)을 넣고 `loadHome` 앞뒤 시간을 잰다. 고치는 방법: 러닝을 한 번만 훑어 "주 시작 → 인정 횟수" Map과 "그날 0시 → 뛴 여부" Set을 만든 뒤 주 연속 · 이번 주 횟수 · 칸 7개를 그 Map/Set으로 계산하면 O(N)이 된다(러닝마다 `startOfWeek` · `startOfDay` 한 번씩). 재어 보고 수십 ms 아래면 그대로 둬도 된다.
- [신규] [제안] [추정] 홈 값 다시 읽기가 겹칠 수 있다: 홈을 띄운 채 앱을 백그라운드로 보냈다가 자정을 넘겨 돌아오면 AppState 'active'의 `reload`와, 밀려 있던 자정 타이머의 `reload`가 거의 동시에 돌아 러닝 전체 읽기 + 계산이 두 번 일어난다(늦게 끝난 요청 무시로 화면 값은 맞다). 또 홈에서 [시작]으로 위치 권한 창이 뜨면 안드로이드에서는 앱이 잠깐 background → active가 되어 그때마다 `reload`(와 `_layout.tsx`의 `syncReminder`)가 한 번 더 돈다 — `components/home/useHomeView.ts` `useFocusEffect` 안의 AppState 구독 · `setTimeout(reload, untilTomorrow)` — 확인한 범위: 패킷 diff의 `useHomeView`를 읽음. 백그라운드 동안 미뤄진 RN 타이머가 복귀 순간에 바로 도는지, 권한 창에서 AppState가 바뀌는지는 실행해 보지 않음 — [확실]이 되려면 `reload`에 임시 로그를 넣고 "자정 넘겨 복귀" · "위치 권한 창 닫기"를 해 본다. 고치는 방법: `reload`가 돌 때마다 자정 타이머를 지우고 다음 자정으로 다시 거는 방식으로 바꾸면 복귀 때 한 번만 읽는다. 권한 창 때문에 생기는 한 번은 비용이 작아 그대로 둬도 된다.
