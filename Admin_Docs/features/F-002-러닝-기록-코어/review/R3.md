## 지적 (있을 때)
- [위험] [추정] 종료(finishRunSession)가 끝나는 동안 타이머 · 위치 · 알림 버튼이 상태를 계속 바꾼다. `points = unsavedPoints`(배열 참조)를 잡은 뒤 `await writeQueue`와 `await saveFinishedRun` 사이에도 state가 살아 있고 타이머가 돈다. 이때 advance → queueSave가 같은 배열을 가져가 saveProgress로 한 번 더 쓰면 run_points가 중복된다. 또 saveFinishedRun은 writeQueue 밖이라, 늦게 실행된 saveProgress가 runs.status를 'active'/'paused'로 되돌리고 active_run 줄을 다시 만들 수 있다(다음 실행에 이미 끝난 러닝의 복구 창이 뜸). 종료 중 알림 [재개]가 눌려도 summary와 state가 어긋난다. — services/runController.ts finishRunSession · queueSave — 코드만 읽음(실행 안 함, DB의 exclusive 트랜잭션 순서는 확인 못 함). 확인 방법: saveFinishedRun mock을 느리게 만들고 그 사이 타이머를 1초 진행시키는 테스트를 쓰면 saveProgress 호출 순서와 points 중복 여부가 드러나 [확실]이 된다 — 고치는 방법: finishRunSession 맨 앞에 `finishing` 플래그를 두고 advance · queueSave · pause · resume이 그동안 무시하게 한다. 마지막 저장은 writeQueue 안에서 하고, 실패하면 플래그를 푼다. 점은 저장 직전에 한 번만 가져간다.
- [주의] [확실] 종료를 동시에 두 번 부르는 것을 컨트롤러가 막지 않는다. active.tsx의 `finishStarted` ref로만 막는다. 두 호출 모두 `if (!state)` 를 통과하면 saveFinishedRun이 두 번 돌아 run_points가 두 배로 들어간다(run_points에 중복 방지 제약 없음). 같은 이유로 startRunSession도 `state`를 insertRun 뒤에야 채워서, 동시 두 번 호출 시 러닝 2건이 만들어진다. — runController.ts finishRunSession · startRunSession, db/runsRepo.ts saveFinishedRun, db/schema.ts run_points — 코드 읽음. 현재 호출 경로는 화면 쪽 가드가 하나씩 있어 평소엔 안 일어남 — 고치는 방법: 컨트롤러에 진행 중인 종료 · 시작의 Promise를 보관해 같은 Promise를 돌려준다. 점 저장은 중복 방지 키를 쓴다.
- [주의] [확실] 위치 시작 실패 때 0초짜리 러닝이 '완료' 기록으로 남는다. `finishRunSession()`이 status='finished'로 저장하므로 listFinishedRuns · 기록 목록에 0초 · 0km 러닝으로 보인다. 또 이때 finishRunSession이 저장 실패로 null을 돌려주면 state가 남아 다음 시작이 `already-running`으로 막히고, 홈 복구 확인은 "기록 중"으로 보고 /run/active로 보낸다. — runController.ts startRunSession catch 분기, runsRepo.ts listFinishedRuns — 코드 읽음 — 고치는 방법: 시작에 실패한 러닝은 runs 행을 지우는(또는 status를 따로 두는) 함수로 정리하고, 정리에 실패해도 state를 null로 되돌린다.
- [주의] [확실] 알림 권한을 요청하는 곳이 없다. `requestNotificationAccess`는 정의만 있고 호출하는 곳이 없다(app/src 전체 grep). Android 13 이상에서는 권한이 없으니 showRunControl이 조용히 반환해 잠금화면 [일시정지]/[재개] 버튼이 뜨지 않는다. 사용자에게 알리는 것도 없다. 코드는 "권한 없으면 버튼 없이 진행"으로 안전하게 처리하지만, 권한을 받는 흐름이 빠져 기능이 실질적으로 꺼져 있다. — services/permissions.ts, runNotification.ts showRunControl, git grep 결과 — 고치는 방법: 시작 흐름(useStartRun)에서 위치 권한 뒤에 알림 권한을 한 번 요청하고, 거절돼도 진행하되 토스트로 알린다. 의도(나중 기능으로 미룸)라면 feature.md에 적는다.
- [주의] [추정] 앱 프로세스가 위치 작업으로 다시 살아나는 경로가 실제로는 동작하지 않을 수 있다. 위치 listener는 runController의 beginTracking · checkPendingRun에서만 `setLocationListener(handleLocations)`로 등록된다. 새 프로세스에서는 `listener`가 null이라 runLocation의 작업이 `listener?.(fixes)`에서 위치를 버린다. `restoreAndContinue`와 테스트 "화면 없이 프로세스만 다시 살아나…"는 handleLocations를 직접 부르므로 이 연결 누락을 못 잡는다. — runLocation.ts defineTask · setLocationListener, runController.ts handleLocations, _layout.tsx(runLocation만 import) — 호출 위치 grep으로 확인. 새 프로세스에서 작업이 실제로 불리는지는 못 봄. 확인 방법: 에뮬레이터에서 러닝 중 최근 앱 목록에서 앱을 밀어낸 뒤 DB의 run_points가 늘어나는지 본다 — 고치는 방법: runController를 모듈 최상단에서 `setLocationListener(handleLocations)`로 등록하고 _layout에서 import한다.
- [주의] [추정] 위치 받기를 끄지 못하면 그대로 남는다. 종료 후 `Promise.allSettled`로 실패를 삼키고, stopLocationUpdates도 isLocationRunning이 오류에 false를 돌려주면 stop을 건너뛴다. 다음 실행의 checkPendingRun은 active_run이 없으면 바로 null을 돌려 남은 위치 작업을 정리하지 않는다. 결과는 포그라운드 서비스 알림과 GPS가 계속 켜져 있는 것이다. continuePendingRun 실패 분기도 위치를 끄지 않는다. — runController.ts finishRunSession · checkPendingRun · continuePendingRun, runLocation.ts stopLocationUpdates — 코드 읽음, 실제 실패 상황은 재현 못 함 — 고치는 방법: checkPendingRun에서 저장된 러닝이 없고 상태도 null일 때 `isLocationRunning()`이면 끈다.
- [제안] [확실] 테스트가 놓친 예외: (1) savePendingRun 저장 실패(null 반환) 테스트 없음 (2) 위치 시작 실패 분기에서 finishRunSession까지 실패하는 경우 (3) 종료 중 타이머 · 위치 도착, 종료 · 시작 동시 호출 (4) startRunControl · prepareVoice · Speech 등의 실패 (mock이 전부 성공만 돌려줌) (5) 위치 권한 거부 · GPS 꺼짐 · 알림 권한 없음을 다루는 useStartRun · permissions · showRunControl 테스트 없음 (6) runsRepo SQL의 롤백 · 중복은 에뮬레이터 확인만 있고 단위 테스트가 없음. — runController.test.ts 테스트 이름 목록 · 패킷 설명 — 고치는 방법: 위 [위험] · [주의] 수정과 같이 (1)(2)(3)을 runController 테스트에 넣는다. runsRepo는 in-memory SQLite(better-sqlite3 등)로 saveProgress · saveFinishedRun의 롤백을 시험하는 것을 고려한다.
