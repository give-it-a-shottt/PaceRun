## 지적 (있을 때)
- [주의] [확실] 러닝 중 1초마다 부르는 `saveProgress`가 `withExclusiveTransactionAsync`를 써서, 저장할 때마다 SQLite 연결을 새로 열고(`Transaction.createAsync` → `useNewConnection: true` + `initAsync`) 끝나면 닫는다. 1시간 러닝이면 연결을 3,600번 열고 닫는다. 새 연결에는 `getDb()`가 거는 `PRAGMA foreign_keys = ON`도 걸리지 않는다(연결마다 따로 거는 설정) — app/src/db/runsRepo.ts `saveProgress`(`saveFinishedRun`도 같은 방식이지만 한 번만 부름) — diff와 app/node_modules/expo-sqlite/src/SQLiteDatabase.ts 180~207행 · 800~806행 확인. 기기에서 걸리는 시간은 재지 않았다 — runController의 `writeQueue`가 이미 쓰기를 한 줄로 세우고 있으니 공용 연결의 `withTransactionAsync`로 바꾸거나, 러닝을 시작할 때 쓰기 전용 연결을 한 번 열어(foreign_keys도 켜서) 끝날 때 닫는다.
- [제안] [확실] 위치 '항상 허용'을 기능에 필요한 것보다 넓게 요청한다. 시작 흐름이 '앱 사용 중' 권한을 받으면 이어서 `requestBackgroundPermissionsAsync`를 부르지만, 기록은 포그라운드 서비스로 '앱 사용 중' 권한만으로 돌고(feature.md 60행), 돌려받은 `background` 값은 어디서도 쓰지 않는다. app.json에 선언한 ACCESS_BACKGROUND_LOCATION 때문에 Play 스토어 심사에서 백그라운드 위치를 쓰는 이유를 따로 신고해야 한다 — app/src/services/permissions.ts `requestLocationAccess`, app/src/components/run/useStartRun.ts `start`, app/app.json(2c231d0) — diff, `git grep`으로 `.background`를 쓰는 곳이 없는 것 확인. '항상 허용'은 기획(pacerun-design.md ONB_01_001)에서 정한 것이라 유지할지는 사용자가 정한다 — 빼기로 하면 요청 줄과 app.json의 ACCESS_BACKGROUND_LOCATION · `isAndroidBackgroundLocationEnabled`를 지운다. 유지하면 러닝 시작 흐름이 아니라 온보딩 한 곳에서만 묻는다.
- [제안] [추정] 딥링크(`pacerun://run/countdown?config=...`)로 카운트다운 화면에 바로 들어오면, 위치 권한 · GPS · 끝나지 않은 러닝 확인을 건너뛰고 3초 뒤 러닝이 시작된다. 다른 앱이나 웹 링크로 위치 기록을 켤 수 있고, 강제 종료 뒤 남은 러닝이 있으면 새 러닝의 저장(`active_run` id=1 덮어쓰기)이 그 복구 상태를 덮어 버린다(옛 runs 줄은 'active'로 남는다). `startRunSession`은 메모리의 `state`만 보고 DB의 `active_run`은 보지 않는다 — app/src/app/run/countdown.tsx, app/src/services/runController.ts `startRunSession` — diff와 app.json `scheme` 확인. 실행하지 않았다. `adb shell am start -d "pacerun://run/countdown?config=%7B%22mode%22%3A%22free%22%2C%22targetDurationSec%22%3Anull%7D"`로 시작되는지 보면 [확실]이 된다 — `startRunSession`에서 `loadActiveRun()`이 있으면 시작하지 않고, 카운트다운은 `useStartRun`을 거쳐 들어온 경우(메모리의 1회용 표시 등)에만 진행하고 아니면 홈으로 보낸다.
- [제안] [추정] GPS 신호를 찾는 동안 `hasGoodGpsFix`는 5초가 지나면 JS 쪽에서만 포기하고, 네이티브의 단건 위치 요청(`getCurrentLocation`, 취소 토큰 null, 만료 시간 없음)은 그대로 둔다. `useStartRun`은 신호를 찾을 때까지 상한 없이 약 7초마다 새 요청을 보내므로, 신호가 안 잡히는 동안 요청이 겹쳐 쌓일 수 있고 [취소] 뒤에도 진행 중이던 요청은 남는다 — app/src/services/gps.ts, app/src/components/run/useStartRun.ts, app/node_modules/expo-location/android/.../LocationHelpers.kt `prepareCurrentLocationRequest` · `requestSingleLocation` — 코드만 읽었다. GPS를 끈 채 'GPS 찾는 중'으로 1분 두고 `adb shell dumpsys location`에서 활성 요청 수를 보면 [확실]이 된다 — 찾는 동안에는 `watchPositionAsync` 하나만 켜 두고 찾았거나 취소하면 `remove()`하거나, 전체 대기 시간에 상한을 둔다.
- [제안] [추정] 화면이 꺼져 있거나 앱이 뒤로 가 있어도 `publish`가 매초 store를 갱신해 러닝 화면이 다시 그려진다. 위치 콜백과 1초 타이머가 둘 다 `advance → publish`를 불러 초당 최대 2번이다. 긴 러닝에서 배터리를 쓴다 — app/src/services/runController.ts `advance` · `publish` · `startTimer`, app/src/app/run/active.tsx(`run` · `now` 구독) — diff 확인, 리렌더 횟수는 재지 않았다(app.json의 reactCompiler가 켜져 있어 자식 부품은 일부 건너뛸 수 있다). React DevTools Profiler로 화면이 꺼진 동안 커밋 수를 보면 [확실]이 된다 — AppState가 'active'일 때만 publish하고 돌아올 때 한 번 publish하거나, 직전 publish 뒤 900ms가 안 지났으면 타이머 쪽 publish를 건너뛴다.
