## 지적 (있을 때)
- [주의] [확실] 위치 '항상 허용'(백그라운드 위치)을 꼭 필요하지 않은데도 요청한다. '앱 사용 중' 권한을 받자마자 바로 이어서 요청하고, 그 전에 왜 필요한지 설명하는 화면도 없다. 기록은 포그라운드 서비스와 '앱 사용 중' 권한만으로 된다(feature.md "설계 의도와 다른 점"). 그런데도 앱 설정에 ACCESS_BACKGROUND_LOCATION과 `isAndroidBackgroundLocationEnabled: true`가 켜져 있다. 이 상태로 Play 스토어에 올리면 백그라운드 위치 사용 신고와 심사를 받아야 하고, 사용자에게도 '항상 위치를 본다'는 인상을 준다 — `app/src/services/permissions.ts` `requestLocationAccess`, `app/app.json` android.permissions · expo-location 플러그인 — 확인 범위: diff의 permissions.ts · useStartRun.ts, 0760d6f의 app.json, feature.md 64줄, D-009. 확인 못 한 것: 앱이 죽었다가 위치 작업으로 되살아나는 경로(`runController.restoreOrStop`)가 실제로 이 권한에 기대는지는 [추정]이다(포그라운드 서비스가 없는 상태라 백그라운드 위치 권한이 있어야 위치가 올 것으로 본다) — 고치는 방법: (가) 요청 · 매니페스트 권한 · 플러그인 설정을 빼고, 프로세스가 죽으면 지금 있는 복구 창(이어서 / 여기까지 저장)으로 처리한다. 또는 (나) 되살아나기 경로 때문에 꼭 남겨야 한다면 D-009에 그 이유를 결정으로 적고, 첫 시작 흐름과 떼어 놓는다. 그리고 따로 설명 화면을 먼저 보여 준 뒤 요청한다.
- [신규] [주의] [추정] 강제 종료 뒤 복구 경로에서는 잠금화면 조작 알림(지울 수 없게 고정된 [일시정지] 버튼 알림)이 지워지지 않는다. 프로세스가 죽어도 이미 띄운 알림은 알림 창에 남는다. 그런데 `savePendingRun`(여기까지 저장)과 `checkPendingRun` · `restoreOrStop`의 '오래 끊김' 분기는 위치 작업만 끄고 `stopRunControl()`은 부르지 않는다. 그래서 눌러도 아무 일도 하지 않는, 지울 수도 없는 알림이 남을 수 있다 — `app/src/services/runController.ts` `savePendingRun` · `checkPendingRun` · `restoreOrStop` — 확인 범위: diff의 runController.ts · runNotification.ts(`sticky: true`). 실행해 보지는 않았다 — 고치는 방법: [확실]이 되려면 러닝 중 `adb shell am kill com.pacerun.app`(force-stop이 아닌 것)으로 프로세스를 죽이고, 다시 열어 [여기까지 저장]을 누른 뒤 `adb shell dumpsys notification`에 pacerun-run-control이 남는지 본다. 남는다면 위 세 경로에서 `stopRunControl()`(알림 지우기)을 함께 부른다.
- [제안] [추정] GPS를 확인할 때 시간 초과가 나도, 이미 보낸 위치 요청은 취소되지 않는다. `hasGoodGpsFix`는 `Promise.race`로 기다림만 끝낸다. 그래서 `getCurrentPositionAsync(BestForNavigation)` 요청은 기기 쪽에서 계속 돈다. 신호를 못 잡는 동안(최대 약 2분, 18번 다시 시도) 요청이 여러 개 겹쳐 GPS를 붙잡고 있을 수 있다 — `app/src/services/gps.ts` `hasGoodGpsFix`, `app/src/components/run/useStartRun.ts` 다시 시도 반복문 — 확인 범위: diff, expo-location `Location.d.ts`(취소 API 없음). 기기 쪽 시간 제한은 확인하지 않았다 — 고치는 방법: [확실]이 되려면 신호가 없는 상태에서 `dumpsys location`으로 남아 있는 요청 수를 본다. 겹친다면 앞 요청이 끝나기 전에는 새 요청을 보내지 않거나, `watchPositionAsync` 하나를 열어 두고 정확도가 충분한 점이 오면 `remove()`하는 방식으로 바꾼다.
- [신규] [제안] [확실] 위치 점을 저장할 때 점 하나마다 `runAsync`를 부른다. 그러면 SQL 문장을 준비하고 → 실행하고 → 정리하는 일을 점마다 되풀이한다(네이티브 호출 3번). 평소에는 1초에 1~2개라 괜찮다. 하지만 저장이 실패하다 다시 될 때나 종료할 때는 밀린 점 수백 개를 한 트랜잭션에서 처리한다. 그동안 다음 매초 저장이 줄 서서 기다린다 — `app/src/db/runsRepo.ts` `insertPoints` — 확인 범위: diff, `node_modules/expo-sqlite/src/SQLiteDatabase.ts` `runAsync`(prepare → execute → finalize) — 고치는 방법: 트랜잭션 안에서 `prepareAsync`를 한 번만 하고, 점마다 `executeAsync`만 부른 뒤 `finalizeAsync`로 마무리한다.
- [신규] [제안] [추정] 위치 기록이 든 폰 DB(run_points · active_run)가 안드로이드 자동 백업에 들어갈 수 있다. `app.json`에 `android.allowBackup` 설정이 없다. Expo의 기본값은 백업 허용으로 알고 있다. 사용자 본인 계정으로 백업되므로 남에게 새는 것은 아니지만, 집 위치를 짐작할 수 있는 경로 데이터라 백업에 넣을지는 정해 두는 게 좋다 — `app/app.json` android — 확인 범위: 0760d6f의 app.json만 봤다. 실제로 만들어지는 AndroidManifest는 보지 않았다 — 고치는 방법: [확실]이 되려면 `npx expo prebuild` 결과의 `android:allowBackup`을 본다. 백업에 넣을지 뺄지 정하고, 빼려면 `android.allowBackup: false`를 넣는다. 서버 동기화(D-004)가 생기면 이 결정을 다시 본다.
