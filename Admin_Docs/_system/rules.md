# Admin_Docs 작성 규칙

## 절대 규칙

1. 사용자 작성 칸은 AI가 내용을 지어내지 않는다. 해당 칸: START_HERE의 서비스 소개, 기능의 설계 의도, 리뷰 SUMMARY의 최종 판정, 면접 예상 질문의 답, 열린 질문 중 사용자가 정할 질문의 답. 비어 있으면 질문 1~2개로 묻고, 문장 정리사로 다듬어 승인받은 문장만 적는다. 칸 옆에 (사용자 확인)을 붙인다.
2. 민감 정보 금지: API 키, 비밀번호, 토큰, .env 값, DB 접속 정보, 개인정보(실명·연락처·주소)는 어떤 문서와 커밋 메시지에도 쓰지 않는다. 필요하면 "환경변수 JWT_SECRET 사용"처럼 이름만 쓴다.
3. Admin_Docs는 레포에 커밋한다. .gitignore에 넣지 않는다.
4. 모든 문서는 2층 구조(한눈에 보기 / 개발자 상세)로 쓴다. STATUS.md와 OPEN_QUESTIONS.md는 표 중심이라 한 층만 둔다.
5. 길이: 코드를 몰라도 이해되는 내용이면 짧게 쓴다. 이해가 어려우면 풀어 쓰되 한 항목은 5줄을 넘기지 않는다. 전문 용어를 위층에 쓰면 glossary.md에 추가한다.
6. 표시는 아래 "표시 범례"만 쓴다. 상태 칸에 지적 등급([위험]·[주의])을 쓰지 않는다.
7. 이모지는 💡 ❓ ⚠️ 세 개만 쓴다.
8. 문서와 코드가 다르면 코드를 기준으로 문서를 고치지 않는다. 먼저 사용자에게 어느 쪽이 의도인지 묻는다. 지금 답을 못 받으면 OPEN_QUESTIONS.md에 적어 둔다.
9. 디자인은 다루지 않는다: 색·간격·폰트·컴포넌트 모양·반응형 레이아웃·접근성·색 대비를 Admin_Docs에 쓰지 않고, 리뷰어도 지적하지 않으며, 열린 질문에도 적지 않는다. 디자인의 기준은 pacerun-design.md와 피그마다.
10. 토큰 절약: 리뷰어 서브에이전트는 레포 전체를 탐색하지 않는다. 메인이 만든 리뷰 패킷을 기준으로 보고, 패킷으로 판단이 안 되는 항목만 해당 파일을 직접 연다.
11. AI는 사용자가 정해야 할 것을 추측으로 정하지 않는다. 그런 선택을 만나면 OPEN_QUESTIONS.md에 적고, 작업을 계속할 수 있으면 가장 되돌리기 쉬운 쪽으로 임시 진행한 뒤 그 사실을 질문에 함께 적는다.
12. STATUS에서 [됨]은 확인 방법이 있을 때만 쓴다. 확인 방법이 없으면 [일부]로 둔다.
13. "내가 할 일" 블록이 있는 문서를 고칠 때마다 블록도 함께 맞춘다.

## 이 프로젝트의 위임 규칙 (2026-11-22 사용자 요청)

사용자가 "멈추지 말고 진행, 답도 알아서 최선으로"라고 맡겼다. 그래서 절대 규칙 1·11을 아래처럼 적용한다. 사용자가 확인하면 표시를 (사용자 확인)으로 바꾼다.

| 칸 | 처리 | 표시 |
|---|---|---|
| 서비스 소개 · 설계 의도 | 사용자가 승인한 pacerun-design.md의 내용에서 옮겨 적는다. 문서에 없는 내용은 덧붙이지 않는다 | (AI 초안 — 사용자 위임, 확인 전) |
| 리뷰 최종 판정 | AI가 수용/거절을 정한다. [위험]은 전부 고친다 | (AI 위임 판정) |
| 사용자가 정할 선택 | AI가 정해 decisions/D-00X에 남기고 "바꿔야 하는 조건"을 적는다 | (AI 위임 결정) |
| 면접 예상 질문의 답 | 비워 둔다. "내가 할 일"에 올린다 | — |

## 문장 정리사

사용자가 말한 내용을 문서에 남길 문장으로 다듬는 역할. 사용자 작성 칸에만 쓴다.

- 사용자가 말하지 않은 내용, 이유, 예시를 덧붙이지 않는다.
- 판단의 세기를 바꾸지 않는다.
- 사용자가 쓰지 않은 전문 용어로 바꾸지 않는다.
- 맞춤법, 어순, 군더더기, 중복만 정리한다.
- 애매하면 지어내지 말고 ❓로 한 가지만 되묻는다.
- "❓ 이렇게 남길까요?" 형식으로 보여 주고 OK를 받은 문장만 저장한다. 원문은 저장하지 않는다.

## 표시 범례

| 무엇에 붙나 | 표시 | 뜻 |
|---|---|---|
| 문서·리뷰 전체 상태 | [통과] | 지적이 없거나 [제안]만 있음 |
| | [보완] | [주의] 지적이 있음 |
| | [막힘] | [위험] 지적이 있음. 고치기 전엔 STATUS가 [됨]이 될 수 없음 |
| 지적 하나의 등급 | [위험] | 그대로 두면 잘못 동작하거나 보안 문제가 생김 |
| | [주의] | 지금은 돌아가지만 고치는 게 좋음 |
| | [제안] | 해도 되고 안 해도 됨 |
| 지적의 확신 | [확실] | 해당 코드를 직접 읽고 확인함 |
| | [추정] | 일부만 보고 판단함, 확인이 더 필요함 |
| 2차 이상 리뷰 | [신규] | 이번 회차에 새로 생긴 지적 |
| 기능 진행(STATUS) | [됨] / [일부] / [다음] | 확인까지 끝남 / 진행 중이거나 확인 방법 없음 / 시작 전 |
| 질문(OPEN_QUESTIONS) | [열림] / [닫힘] | 아직 답 없음 / 답이 다른 문서로 옮겨짐 |

지적 한 줄의 표시 순서: [신규] [등급] [확신] 내용

## 확신 표시 기준

- [확실]: 해당 코드를 직접 읽고(패킷의 diff 또는 직접 연 파일) 문제를 확인했다. 테스트 실패처럼 결과로 드러난 것도 [확실]이다.
- [추정]: 패킷의 일부만 보고 판단했거나, 관련 파일을 열지 않았거나, 실행해 보지 않으면 확실히 알 수 없다.
- 확인한 범위: 실제로 본 것을 짧게 쓴다.
- [추정] 지적은 "무엇을 확인하면 [확실]이 되는지"를 고치는 방법 앞에 한 줄로 적는다.

## STATUS 상태 기준

- [됨]: 설계 의도의 완료 기준을 모두 충족했고, 확인 방법(테스트 통과, 직접 실행 결과, 리뷰 [통과] 중 하나 이상)이 있다.
- [일부]: 만들기 시작했거나 일부만 되거나, 됐지만 확인 방법이 없다. 한 줄 설명에 무엇이 빠졌는지 적는다.
- [다음]: 할 예정이지만 시작 전이다.
- 확인 방법 칸에는 실제로 한 확인만 적는다. 리뷰 결과가 [막힘]이면 [됨]이 될 수 없다. 확인이 리뷰 [통과]뿐이면 "실행 확인 없음"을 함께 적는다.
- 이 프로젝트 추가 기준: 화면 꺼진 상태의 GPS · 소리 안내처럼 실기기에서만 확인되는 완료 기준이 있는 기능은, 실기기 확인 전까지 [일부]로 둔다.

## 질문 규칙

- 누가 정해야 하나: 사용자(설계 결정) / 공부(사용자가 이해하고 싶은 원리) / AI 확인(AI가 코드·문서를 더 보면 풀리는 것)
- 임시 처리는 가장 되돌리기 쉬운 쪽으로만 한다.
- [열림] 표는 "사용자" 질문을 맨 위에 둔다. 디자인 질문은 적지 않는다.
- 닫을 때 답 내용은 OPEN_QUESTIONS에 다시 쓰지 않고 "답이 옮겨진 곳"만 적는다.

## "내가 할 일" 블록

- START_HERE.md, STATUS.md, feature.md, SUMMARY.md는 제목 바로 아래에 "## 내가 할 일" 블록을 둔다.
- 할 일 하나에 한 줄, "무엇을 → 어디서" 형식. 없으면 "없음" 한 줄. 블록은 지우지 않는다.
- R1~R4.md, REVIEW_LOG.md, _system/ 파일은 제목 아래에 "AI 근거용 — 사용자는 안 읽어도 됨" 한 줄을 둔다.

## 범위 밖

⚠️ 디자인(색·간격·폰트·컴포넌트 모양·반응형 레이아웃·접근성·색 대비)은 검수 범위 밖이다. 사용자가 직접 평가한다.

⚠️ 배포, 서버 인프라, CI는 현재 검수 범위 밖이다. 실제 배포를 시작하면 R5 배포·운영 리뷰어(환경 분리, 로그, 모니터링, 롤백 방법)를 추가한다.
