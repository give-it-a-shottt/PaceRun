# D-007 러닝 번호는 폰에서 만들고, 경로는 한 칸에 통째로 둔다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]
무엇을: ① 러닝마다 폰이 고유 번호(UUID)를 만들고 서버도 그 번호를 그대로 쓴다. ② 서버는 경로(위치 점 목록)와 구간 기록을 러닝 한 줄 안에 통째로 넣는다. (AI 위임 결정 — ①의 근거는 pacerun-design.md "기록마다 고유 ID로 중복 방지")
왜: ① 같은 기록을 여러 번 올려도 한 건만 남는다. ② 경로는 항상 러닝 하나 단위로 통째로 읽기 때문에 나눠 둘 이유가 없다.

## 개발자 상세
- 올리기: `PUT /runs/{id}`. 같은 번호가 이미 내 것이면 덮어쓰고(200), 없으면 새로 저장(201).
- 남의 번호: 같은 번호가 다른 회원의 러닝이면 409를 돌려준다. 폰이 번호를 정하므로, 이 확인이 없으면 남의 기록을 덮어쓸 수 있다.
- route는 JSONB `[[lat, lng, elapsed_s], …]`, 최대 20000개(약 5시간 반).

| 후보 | 장점 | 단점 |
|---|---|---|
| A. 폰 UUID + JSONB (선택) | 재시도에 안전, 조회 1번 | 경로 안의 점을 조건으로 검색 못 함 |
| B. 서버가 번호 발급 | 번호 충돌 걱정 없음 | 응답을 못 받고 재시도하면 중복 저장 |
| C. 점마다 한 줄(run_points 테이블) | 점 단위 검색 가능 | 줄 수가 많고, 지금은 그런 검색이 없음 |

- 결과로 생기는 제약: 목록 조회에서는 route · segments를 빼고 요약만 준다(응답이 커지지 않게).
- 이 결정을 바꿔야 하는 조건: "이 지점을 지난 러닝 찾기"처럼 경로 안을 검색해야 할 때 → C 또는 PostGIS.
