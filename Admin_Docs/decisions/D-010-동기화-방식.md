# D-010 동기화는 "폰이 올린다" 한 방향이 기본이다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]
무엇을: 기록의 원본은 폰이다. 폰이 끝난 러닝을 서버로 올리고(자동), 서버에서 폰으로 내려받는 것은 로그인한 직후와 [지금 동기화]를 눌렀을 때만 한다. 올라간 러닝은 다시 고치지 않는다. (AI 위임 결정)
왜: 💡 비유: 가계부를 내 수첩에 먼저 적고 사본을 은행에 보내는 것 — 수첩이 원본이라 은행 것과 다를 일이 없다. 양쪽에서 고칠 수 있게 하면 "어느 쪽이 맞나"를 정하는 규칙이 필요한데, 러닝 기록은 끝나면 바뀌지 않으므로 그럴 이유가 없다.

## 개발자 상세
- 상황: 계정을 연결하면 폰 기록을 서버에 올리고(웹 대시보드용), 새 폰에서는 서버 기록을 받아야 한다(pacerun-design.md Flow E). 기획은 "기록마다 고유 ID로 중복 방지", "오프라인 중 로그인 만료 → 대기열 유지, 다시 로그인하면 업로드"까지만 정했다.

| 후보 | 장점 | 단점 |
|---|---|---|
| A. 올리기는 자동, 내려받기는 로그인 직후 · 수동 (선택) | 평소에는 요청 몇 개로 끝남. 충돌이 생길 수 없음 | 다른 폰에서 올린 기록은 [지금 동기화]를 눌러야 보임 |
| B. 매번 올리기 + 내려받기 | 여러 폰이 늘 같음 | 앱을 켤 때마다 서버 목록을 끝까지 읽어야 함(기록이 쌓일수록 무거움) |
| C. 바뀐 것만 받는 방식(마지막 받은 시각 이후) | 가볍고 늘 같음 | 서버 API에 "이 시각 이후" 조회가 없어 서버를 고쳐야 함 |

- 결정
  - 올리기: 러닝을 끝냈을 때, 앱을 켰을 때, 앱으로 돌아왔을 때, [지금 동기화]. 폰의 `runs.sync_state`가 `local`인 끝난 러닝을 오래된 것부터 `PUT /runs/{id}`로 보내고 성공하면 `synced`로 바꾼다. "대기열"은 따로 만든 표가 아니라 이 칸이다.
  - 내려받기: 로그인(가입) 직후와 [지금 동기화]. `GET /runs`를 끝까지 넘기며 폰에 없는 번호만 `GET /runs/{id}`로 받아 넣는다. 폰에 있는 번호는 건드리지 않는다.
  - 멈추는 경우와 건너뛰는 경우를 나눈다: 서버에 닿지 못함 · 서버 오류(5xx) · 로그인 만료 → 거기서 멈추고 남은 기록은 다음에 올린다. 서버가 "이 기록은 받을 수 없다"(409 · 413 · 422)고 하면 그 기록만 건너뛰고 계속한다(다시 보내도 같으므로 앱을 켜 둔 동안에는 다시 보내지 않는다).
  - 주 목표는 폰의 값이 기준이다. 동기화할 때 서버에 올린다(웹 대시보드의 "주 목표 달성 주 수"가 같은 기준이 되게). 서버의 값을 폰으로 가져오지 않는다.
  - 로그아웃해도 폰의 기록과 `synced` 표시는 그대로 둔다.
- 결과로 생기는 제약
  - 한 폰에서 계정을 바꿔 쓰면 섞인다: 앞 계정으로 올린 러닝은 `synced`라 새 계정으로 올라가지 않고, 아직 올리지 않은 러닝은 새 계정으로 올라간다. 1인용 앱이라 다루지 않았다.
  - 서버에서 지운 기록이 폰에서 지워지지 않는다(지금은 지우는 기능이 어디에도 없다).
  - 두 폰을 함께 쓰면 다른 폰의 기록은 [지금 동기화]를 눌러야 들어온다.
- 이 결정을 바꿔야 하는 조건: 기록을 고치거나 지우는 기능이 생길 때, 폰 여러 대를 늘 같게 맞춰야 할 때(→ C로 가고 서버에 "이 시각 이후 바뀐 것" 조회를 더한다).
